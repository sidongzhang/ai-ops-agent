# 诊断中断与成本控制设计（v2 · 基于官方原生能力）

> 状态：**计划（待评审）**，未改业务代码。
> v1 的自研"取消标志 + 证据缓存"已废弃：pydantic-ai 有**官方原生取消与历史继续**，直接复用。
> 适用范围：**第一批只做 停止 / 历史继续 / 预算 / 费用记录**。不迁 LangGraph、不引入 Temporal、不做语义结论缓存、不更换实时通信协议。

## 0. 结论（先看这个）

| 问题 | 结论 |
|---|---|
| 框架支持吗？ | **支持，且是原生一等公民**：`CancellationToken` + `RunCancelled`（带完整消息历史与用量） |
| 我们现在能用吗？ | **不能**。我们是 `pydantic-ai-slim 2.0.0`，原生取消在 **2.26.0** 才引入 |
| 升级可行吗？ | **可行**。`uv lock` 实测只动 5 个包、无冲突（见 §1.3） |

```python
async def stream_turn(agent, prompt, history, token, on_text):
    try:
        async with agent.run_stream(prompt, message_history=history, cancellation_token=token) as result:
            async for delta in result.stream_text(delta=True):
                on_text(delta)
        return result.all_messages(), False
    except RunCancelled as exc:
        return exc.all_messages(), True      # ← 取消时框架交出「已完成的完整历史」
```

## 2. 五个问题的设计

### 2.1 取消指令怎么到达真正在跑的进程 / 何时显示"正在停止""已停止"
**执行事实**：诊断在 `BackgroundTasks` 的**线程**里 `run_sync`（同步阻塞）；取消请求走另一个线程。

官方依据（`docs/agent.md`）：
> "Calling `token.cancel()` from another thread is the only way to interrupt a synchronous run while it is blocked."
> "`cancel()` is idempotent and thread-safe. One token may govern multiple concurrent runs, cancelling all of them."

**设计（与执行器解耦的三层）**
1. **进程内注册表（快路径）**：`report_id → CancellationToken`。取消请求直接 `token.cancel()`，**立即生效**（同线程安全由框架保证）。
2. **DB 标志（真相来源）**：`cancel_requested_at`。保证可审计、可兜底、跨重启可见。
3. **Redis 发布订阅（跨进程通道）**：频道 `aiops:diagnosis:cancel`。多 worker / 未来迁 Celery 时，运行方监听并取消本地 token；**协议不变**。

**状态机与文案**
```
running ──(收到取消请求)──> stopping ──(运行方落终态)──> cancelled
   │                                              └(进程失联/超时)──> failed（标注"无可恢复历史"）
   └──(取消早于启动)──> 原生保证：已取消的 token 使该 run 不启动 → cancelled（零请求）
```
| 状态 | 判定条件 | 用户看到 |
|---|---|---|
| `stopping` | `cancel_requested_at != null` 且 `status='running'` | 「正在停止…」按钮转圈 |
| `cancelled` | 运行方写出终态（含历史/用量） | 「已停止 · 已采集 N 步 · 消耗 X tokens · **可继续**」 |
| `cancelled(不可恢复)` | reaper 收尸（进程死/硬杀） | 「已停止 · **未取到完整历史**」（不谎称可继续） |

**竞态**：官方原生提供保证 —— "passing an already-cancelled token to a run prevents that run from starting (which also closes the 'cancel raced ahead of the run' gap)"。即**取消到了但任务还没开跑 → 不会启动**，天然不花冤枉钱。

### 2.2 如何用原生取消，且不触发重试／备用模型／子 Agent 继续跑
| 风险 | 现状 | 改法（位置） |
|---|---|---|
| **被 `except Exception` 吞掉** | `runner.py` 两处 `except Exception` → 走 `_fallback_api_model` / `_run_text_fallback` | 在**两处最前面**加 `except RunCancelled: raise`（或捕获后直接返回 `cancelled` 结果），**绝不进入降级分支**。依据：`RunCancelled` MRO 含 `Exception` |
| **框架重试** | 我们传 `retries=3`（工具重试/输出校验预算） | 取消是**运行终止**而非可重试错误；`docs/retries.md` 未把取消列为可重试项。**验收用例①/②实测断言**：取消后不得出现第二次模型请求（依据：不承诺，用测试证明） |
| **备用模型** | 本地模型失败→API 模型；API 失败→纯文本 | 取消路径显式短路，且 `_fallback_api_model` 调用点加"取消中则跳过"判断 |
| **子 Agent 继续跑** | `investigate` 子代理、`consult_specialists` 专家各自 `run_sync` | **同一个 token 传入子代理**（官方："one token may govern multiple concurrent runs, cancelling all of them"）。实现：`AgentDeps.cancel_token`，在 `tools.py` 子代理调用处与 `specialists.run_specialists` 里透传 `cancellation_token=` |
| **工具执行中被取消后的历史** | — | 官方自动修复：为悬空工具调用合成 `ToolReturnPart(outcome='interrupted', metadata={'pydantic_ai_synthesized_tool_return': True})`；已完成的结果**保留**（#10049） |

> 明确不承诺：**取消不保证"零费用"**。在途的那一次模型请求可能已经产生计费；能保证的是"**不再发下一轮**"。省多少取决于取消时机（工具间隙取消最省）。

### 2.3 完整消息历史 / 已完成工具结果 / 用量的保存与恢复
**口径纠正**：v1 说的"保存证据后重新提交问题"**不是**断点恢复。真正的恢复 = **原生消息历史 + 用量 + 会话标识**，证据只是其中的内容。

保存（取消/正常结束时都做）：
| 内容 | 取法 | 说明 |
|---|---|---|
| 完整消息历史 | `exc.all_messages()` / `all_messages_json()`（`RunCancelled` 自带）；正常结束用 `result.all_messages()` | 含 `ModelRequest`/`ModelResponse`/`ToolCallPart`/`ToolReturnPart`，即**已完成的工具结果**在内 |
| 本次用量 | `exc.usage` / `result.usage()` | 官方在取消时也给出用量 → **可记真实值** |
| 会话/运行标识 | `exc.conversation_id` / `run_id` | 跨轮关联 |

恢复（`POST …/resume` 或带 `resume_report_id` 的提交）：
```python
agent.run_sync(
    message_history=stored_history,      # ← 原生历史
    usage=stored_usage,                  # ← 官方："useful for resuming a conversation"，用量累加
    cancellation_token=new_token,        # ← 单次令牌：一次取消令牌不可复用，必须新铸
    deps=...,
)
```
**未完成的工具调用**（官方语义，须按此实现，不可自己瞎补）：
- 历史末尾若还有"能等到真实结果"的工具调用 → 恢复时**执行它们**（不传新 `user_prompt` 即续跑）。
- 若我们**要放弃**这条悬空调用（用户换话题）→ 必须显式 `repair_messages(history)`，否则框架会**抛错**（"raises rather than abandon them"）。
**过期证据**（框架不管，产品层职责）：
- 恢复时在指令里**显式注入采集时间**：「以下证据采集于 X 分钟前，可能过期；若判定关键，请重新取证」。
- 提供 `force_refresh` 开关，跳过历史中较旧的只读工具结果（重跑相应工具）。
- 绝不把旧结果当新结果呈现；过期阈值按工具类别分档（健康/日志 3min、指标 5min、业务数据 15min、静态 60min）。

### 2.4 复用现有任务基础设施：多进程 / 重复提交 / 重启 / 异常退出
| 场景 | 复用与处理 |
|---|---|
| **执行器** | 继续用 FastAPI `BackgroundTasks`（**不迁 Celery**）。取消协议设计成执行器无关，将来迁 Celery 只换监听端 |
| **多进程取消** | Redis pub/sub（已有 Redis 容器）+ DB 标志。运行方订阅自身 `report_id`；跨进程延迟 = 一次 pub/sub 往返 |
| **重复点击停止** | `token.cancel()` **幂等**；DB 用 `UPDATE … WHERE cancel_requested_at IS NULL`；前端按钮置 loading。二次点击不产生额外状态 |
| **重复提交问题** | 幂等键 `(org_id, system_id, user_id, question_hash, 时间窗)`：命中已有 `running/stopping` 报告则直接返回该报告，不新建 |
| **服务重启（优雅）** | 关停时收到 `CancelledError`（外部取消）→ 用 `RunCancelled.from_cancellation(exc)` 取回附带历史并落库，标 `cancelled`，**可继续** |
| **服务重启 / 硬杀（SIGKILL）** | 无历史可取 → 启动 reaper 把超过 N 分钟的 `running/stopping` 标 `failed`，并显式标注 **"未取到可恢复历史"**（不谎称断点） |
| **Redis 不可用** | 降级：运行中线程每 2s 读一次 DB 标志（只在 `cancel_requested_at` 有值时触发查询，避免常态开销） |

### 2.5 累计用量与费用（含取消 / 重试 / 降级 / 继续）
**记账口径**：一次"诊断会话"= 首次提交 + 若干次取消/继续；**累计**= 各次 `usage` 之和。
| 来源 | 取法 |
|---|---|
| 取消的那一次 | `RunCancelled.usage`（官方在取消时提供）→ 计入 `tokens_cancelled` 与费用 |
| 备用模型 / 文本降级 | 各次调用的 `usage` **累加**（现状是覆盖 → 要修） |
| 继续（resume） | 传入 `usage=prior`，框架累加；落库取最终值 |
| 费用 | 官方 `usage` 携带 `cost`（`genai-prices`）；`UsageLimits.cost_limit` 可做**原生费用上限** |
| **取不到时** | 记 **`usage_complete=false` + `usage_gap_reason`**（如 "provider 未返回用量" / "硬杀丢失"），**绝不写 0 冒充**。前端展示为"≈"/"未知" |

预算（第一批就上，两道与关系）：
1. **框架原生**：`UsageLimits(cost_limit=…, total_tokens_limit=…, request_limit=…, tool_calls_limit=…)`（升级后新增 `cost_limit`）。
2. **会话级**（产品层）：`(org_id, user_id, system_id)` 在时间窗内累计用量/费用，超限**拒绝新提交**并提示，堵住"取消→重问"绕过单次限额。

## 5. 验收矩阵（每项都给"怎么验 + 期望 + 依据"）
| # | 场景 | 怎么验 | 期望 | 依据 |
|---|---|---|---|---|
| ① | **模型请求中停止** | 注入"慢模型"（`FunctionModel` 或 sleep 的 TestModel），请求发出后调 `token.cancel()` | 抛 `RunCancelled`；`exc.usage` 非空；**无第二次模型请求**；落 `cancelled` | 官方 §Cancelling a Run；不承诺零费用 |
| ② | **工具执行中停止** | 用一个可控 sleep 工具；在工具执行期间取消 | 已完成的工具结果**保留**在历史里；悬空调用被合成 `outcome='interrupted'`；`cancelled` 落库 | #7993（≥2.38）、#10049（≥2.55）、`message-history.md` |
| ③ | **停止后继续** | 对 `cancelled` 报告调 resume（`message_history` + `usage=` + 新 token） | 不重跑已完成取证；累计用量=首次+本次；给出结论 | 官方示例 `cancel_and_resume.py`；`usage=` 文档 |
| ④ | **重复点击停止** | 连点 5 次 | 幂等：一次 `RunCancelled`，无额外状态/请求，无 500 | 官方："`cancel()` is idempotent"；token 单次使用 |
| ⑤ | **服务重启后的状态** | (a) 优雅关停（SIGTERM）→ 断言 `from_cancellation()` 存下历史；(b) `kill -9` → 断言 reaper 标 `failed` 且 `resumable=false` | (a) 可继续 (b) 明确"不可恢复"，**不谎称断点** | 官方 §external cancellation；reaper 自研 |
| ⑥ | **预算** | 会话内连续 取消→重问，累计超 `cost_limit` / 会话预算 | 被拒绝并给出明确提示；不产生新模型请求 | `UsageLimits.cost_limit`；会话预算自研 |
| ⑦ | **费用记录** | 正常 / 取消 / 降级 / 继续 各一次 | 四项分别有真实用量；无法取得时 `usage_complete=false` + 原因，**不写 0** | 不承诺精确性，用测试断言字段语义 |
| ⑧ | **租户隔离** | A 租户的历史/用量不出现在 B | 断言隔离 | 多租户红线 |
| ⑨ | **不污染长期记忆** | 取消的诊断 | 不产生 `knowledge_memories` | 沿用现状（仅 success 写） |

回归：`pytest tests -q`（基线 205）+ `scripts/eval-gate.sh` 冒烟 + `--run` 真实评测（验证升级后工具链/提示词行为未漂移）。

## 6. 风险与明确的不承诺
| 风险 | 缓解 |
|---|---|
| `openai` 2→3 大版本 | 只经 pydantic-ai 间接使用；升级后跑全量测试 + 真实诊断 + 评测门禁；必要时临时 pin `openai<3` 验证是否可行 |
| 升级引入行为漂移（提示词/工具选择） | 用现有 evals 门禁做回归；指标下降则回滚到 2.26/2.38 组合 |
| 取消落在长模型请求中 | 只能等该请求结束（或等官方 abort 能力）；**收益仍在**（后续轮全砍） |
| 多进程下 pub/sub 丢消息 | DB 标志为真相来源 + 轮询兜底 |
| 历史 JSON 膨胀 | 只存一份 `diagnosis_run_state`；沿用 `ProcessHistory` 压缩；列表接口不加载该表 |

**明确不承诺**：① 取消后"零费用"；② 固定的节省百分比；③ 硬杀后仍可恢复；④ 框架会替我们管理"证据新鲜度"（这是产品层职责）。
