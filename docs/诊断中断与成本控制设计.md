## 2. 五个问题的设计

### 2.1 取消指令怎么到达真正在跑的进程 / 何时显示"正在停止""已停止"
**执行事实**：诊断在 `BackgroundTasks` 的**线程**里 `run_sync`（同步阻塞）；取消请求走另一个线程。

官方依据（`docs/agent.md`）：
> "Calling `token.cancel()` from another thread is the only way to interrupt a synchronous run while it is blocked."
> "`cancel()` is idempotent and thread-safe. One token may govern multiple concurrent runs, cancelling all of them."

**设计（与执行器解耦的三层）**
1. **进程内注册表（快路径）**：`report_id → CancellationToken`。取消请求直接 `token.cancel()`，**立即生效**（同线程安全由框架保证）。
2. **DB 标志（真相来源）**：`cancel_requested_at`。保证可审计、可兜底、跨重启可见。
3. **Redis 发布订阅（跨进程通道）**：频道 `aiops:diagnosis:cancel`。多 worker / 未来迁 Celery 时，运行方监听并取消本地 token；**协议不变**。

**状态机与文案**
```
running ──(收到取消请求)──> stopping ──(运行方落终态)──> cancelled
   │                                              └(进程失联/超时)──> failed（标注"无可恢复历史"）
   └──(取消早于启动)──> 原生保证：已取消的 token 使该 run 不启动 → cancelled（零请求）
```
| 状态 | 判定条件 | 用户看到 |
|---|---|---|
| `stopping` | `cancel_requested_at != null` 且 `status='running'` | 「正在停止…」按钮转圈 |
| `cancelled` | 运行方写出终态（含历史/用量） | 「已停止 · 已采集 N 步 · 消耗 X tokens · **可继续**」 |
| `cancelled(不可恢复)` | reaper 收尸（进程死/硬杀） | 「已停止 · **未取到完整历史**」（不谎称可继续） |

**竞态**：官方原生提供保证 —— "passing an already-cancelled token to a run prevents that run from starting (which also closes the 'cancel raced ahead of the run' gap)"。即**取消到了但任务还没开跑 → 不会启动**，天然不花冤枉钱。

### 2.2 如何用原生取消，且不触发重试／备用模型／子 Agent 继续跑
| 风险 | 现状 | 改法（位置） |
|---|---|---|
| **被 `except Exception` 吞掉** | `runner.py` 两处 `except Exception` → 走 `_fallback_api_model` / `_run_text_fallback` | 在**两处最前面**加 `except RunCancelled: raise`（或捕获后直接返回 `cancelled` 结果），**绝不进入降级分支**。依据：`RunCancelled` MRO 含 `Exception` |
| **框架重试** | 我们传 `retries=3`（工具重试/输出校验预算） | 取消是**运行终止**而非可重试错误；`docs/retries.md` 未把取消列为可重试项。**验收用例①/②实测断言**：取消后不得出现第二次模型请求（依据：不承诺，用测试证明） |
| **备用模型** | 本地模型失败→API 模型；API 失败→纯文本 | 取消路径显式短路，且 `_fallback_api_model` 调用点加"取消中则跳过"判断 |
| **子 Agent 继续跑** | `investigate` 子代理、`consult_specialists` 专家各自 `run_sync` | **同一个 token 传入子代理**（官方："one token may govern multiple concurrent runs, cancelling all of them"）。实现：`AgentDeps.cancel_token`，在 `tools.py` 子代理调用处与 `specialists.run_specialists` 里透传 `cancellation_token=` |
| **工具执行中被取消后的历史** | — | 官方自动修复：为悬空工具调用合成 `ToolReturnPart(outcome='interrupted', metadata={'pydantic_ai_synthesized_tool_return': True})`；已完成的结果**保留**（#10049） |

> 明确不承诺：**取消不保证"零费用"**。在途的那一次模型请求可能已经产生计费；能保证的是"**不再发下一轮**"。省多少取决于取消时机（工具间隙取消最省）。

### 2.3 完整消息历史 / 已完成工具结果 / 用量的保存与恢复
**口径纠正**：v1 说的"保存证据后重新提交问题"**不是**断点恢复。真正的恢复 = **原生消息历史 + 用量 + 会话标识**，证据只是其中的内容。

保存（取消/正常结束时都做）：
| 内容 | 取法 | 说明 |
|---|---|---|
| 完整消息历史 | `exc.all_messages()` / `all_messages_json()`（`RunCancelled` 自带）；正常结束用 `result.all_messages()` | 含 `ModelRequest`/`ModelResponse`/`ToolCallPart`/`ToolReturnPart`，即**已完成的工具结果**在内 |
| 本次用量 | `exc.usage` / `result.usage()` | 官方在取消时也给出用量 → **可记真实值** |
| 会话/运行标识 | `exc.conversation_id` / `run_id` | 跨轮关联 |

恢复（`POST …/resume` 或带 `resume_report_id` 的提交）：
```python
agent.run_sync(
    message_history=stored_history,      # ← 原生历史
    usage=stored_usage,                  # ← 官方："useful for resuming a conversation"，用量累加
    cancellation_token=new_token,        # ← 单次令牌：一次取消令牌不可复用，必须新铸
    deps=...,
)
```
**未完成的工具调用**（官方语义，须按此实现，不可自己瞎补）：
- 历史末尾若还有"能等到真实结果"的工具调用 → 恢复时**执行它们**（不传新 `user_prompt` 即续跑）。
- 若我们**要放弃**这条悬空调用（用户换话题）→ 必须显式 `repair_messages(history)`，否则框架会**抛错**（"raises rather than abandon them"）。
**过期证据**（框架不管，产品层职责）：
- 恢复时在指令里**显式注入采集时间**：「以下证据采集于 X 分钟前，可能过期；若判定关键，请重新取证」。
- 提供 `force_refresh` 开关，跳过历史中较旧的只读工具结果（重跑相应工具）。
- 绝不把旧结果当新结果呈现；过期阈值按工具类别分档（健康/日志 3min、指标 5min、业务数据 15min、静态 60min）。

### 2.4 复用现有任务基础设施：多进程 / 重复提交 / 重启 / 异常退出
| 场景 | 复用与处理 |
|---|---|
| **执行器** | 继续用 FastAPI `BackgroundTasks`（**不迁 Celery**）。取消协议设计成执行器无关，将来迁 Celery 只换监听端 |
| **多进程取消** | Redis pub/sub（已有 Redis 容器）+ DB 标志。运行方订阅自身 `report_id`；跨进程延迟 = 一次 pub/sub 往返 |
| **重复点击停止** | `token.cancel()` **幂等**；DB 用 `UPDATE … WHERE cancel_requested_at IS NULL`；前端按钮置 loading。二次点击不产生额外状态 |
| **重复提交问题** | 幂等键 `(org_id, system_id, user_id, question_hash, 时间窗)`：命中已有 `running/stopping` 报告则直接返回该报告，不新建 |
| **服务重启（优雅）** | 见 §2.4.2：**主动 cancel token → 等待落库 → 超时兜底** |
| **服务重启 / 硬杀（SIGKILL）** | 无历史可取 → 启动 reaper 把超过 N 分钟的 `running/stopping` 标 `failed`，并显式标注 **"未取到可恢复历史"**（不谎称断点） |
| **Redis 不可用 / 丢消息** | 见 §2.4.3：**DB 轮询是兜底真相源**，Redis 只是加速通道；巡检循环同时覆盖"取消早于 token 注册"与"完成/取消竞态" |

#### 2.4.1 取消通道的三层职责（不可混淆）
| 层 | 角色 | 失败时 |
|---|---|---|
| 进程内注册表 `report_id → token` | **快路径**（同进程零延迟） | 未命中属正常（跨进程/时序） |
| DB `cancel_requested_at` | **真相来源**（可审计、可兜底、跨重启可见） | 不可用则拒绝取消并明确报错（不假装成功） |
| Redis pub/sub | **跨进程加速**（可选） | **丢消息不影响正确性**，靠 DB 轮询补偿 |

#### 2.4.2 真实 SIGTERM 下的关停流程（**补正 2**）
**现状问题**：`BackgroundTasks` 里的 `run_sync` 阻塞在一个工作线程；uvicorn 收到 SIGTERM 后进入关停，**默认不会等我们落库**，进程退出 → 历史丢失。

**设计（挂在既有 lifespan 的 shutdown 段）**
```
收到 SIGTERM（uvicorn 触发 ASGI lifespan shutdown）
 1. 置进程级 shutting_down=True  → 拒绝新诊断提交（返回 503 + Retry-After）
 2. 对本进程注册表内所有 in-flight token 调 token.cancel()   ← 官方：这是中断阻塞中 run_sync 的唯一方式
 3. 有界等待：逐个等待"已落库"信号，总预算 diagnosis_shutdown_grace_seconds（默认 15s，可配）
      - 等待对象是「report 已写终态」事件，不是线程对象（避免 join 卡死）
      - 每 0.5s 检查一次已完成集合，打印剩余数量
 4. 宽限期到仍有未落库 → 记为 usage_complete=false + gap_reason=process_killed，
    写入可恢复标记 resumable=false，并写审计事件 diagnosis.shutdown_unpersisted
 5. 放行退出（uvicorn graceful shutdown 继续）
```
**同时配置**：`uvicorn --timeout-graceful-shutdown`（≥ 宽限期）保证框架不早于我们退出；README/启动脚本里同步 `stack-launcher.sh` 的启动参数。

**语义边界（写进文档，避免误用）**：
- 优雅关停走 **ASGI lifespan**，`run_sync` 解除阻塞后抛的是 `RunCancelled`（我们主动 cancel 的 token）→ 可拿 `all_messages()` + `usage`。
- 若外部强杀（SIGKILL）或宽限期耗尽 → **不可恢复**，`resumable=false`，前端不得显示"可继续"。
- 关停期间**不启动新的诊断**（第 1 步），避免"刚提交就被杀"的坏体验。

#### 2.4.3 DB 轮询循环（**补正 3**，覆盖三种竞态）
**统一巡检循环**（随诊断启动，随诊断结束；默认 2s + 抖动，避免同刻抖动打 DB）
```
on_run_start(report_id, token):          # 注册后立刻自检，堵"取消早于 token 注册"
    if db.cancel_requested(report_id): token.cancel(); return
    spawn poller(report_id, token)

poller(report_id, token):
    deadline = monotonic() + diagnosis_max_run_seconds
    while not monotonic() > deadline:
        sleep(poll_interval + jitter)
        if terminal_written(report_id): break          # ① 完成/取消竞态：谁先落终态谁赢
        if db.cancel_requested(report_id): token.cancel(); break
    # 循环只有一个出口：落终态 / 已取消 / 超时（超时交由 reaper）
```
| 竞态 | 处理 |
|---|---|
| **Redis 丢消息** | 不依赖 pub/sub 正确性：poller 是兜底；pub/sub 只让取消"更快"（正常情况下 <100ms 生效） |
| **取消早于 token 注册**（报告已建，运行方还没注册 / 进程刚重启） | 注册后**立即自检一次 DB 标志**；且官方语义保证"**已取消的 token 使该 run 不启动**" → 零请求 |
| **完成与取消同时发生** | 终态写入用**条件更新**：`UPDATE … SET status='cancelled' WHERE id=? AND status IN ('running','stopping')`；若已 `success` 则取消变为 no-op，接口返回最终状态（200 + `status=success`），只在审计里记 `cancel_requested_at`（**不允许把成功覆盖成取消**，也不允许把取消覆盖成成功） |
| **poller 自身异常** | 单次异常不退出循环（记日志继续）；连续 N 次失败则降级为"每 30s 一查"并告警 |

**取消的幂等语义**（三层各管一段）：API 层 `WHERE cancel_requested_at IS NULL`（可重复调用、只有一个写成功）；框架层 `token.cancel()` 幂等；终态层条件更新。


### 2.5 用量与费用：完整性、估算性质、单次增量与会话累计（**补正 1、5**）

#### 2.5.1 三条硬结论（先纠正常见误判）
1. **"有 usage" ≠ "用量完整"**。`usage` 是**已完成的模型请求**的汇总；被中断的在途请求可能**不返回用量**。所以完整性必须**单独判定**，不能因为字段非空就当完整。
2. **`cost` 是估算，不是账单**。官方 `usage.cost` 由 `genai-prices` 的价格表推算，随官方调价/模型改名而漂移。展示必须标 **"≈"**，并记录**价格表版本**。
3. **预算判定不能依赖"测到的用量"**，否则"用量不完整"就成了绕过预算的口子。预算使用 **测量值 + 保守预留（reserve）**；展示只显示测量值并标注估算。

#### 2.5.2 完整性判定（每 run 一条，落库）
| 标记 | 判定 |
|---|---|
| `usage_complete=true` | 该 run 的**每一次**模型请求都返回了用量，且结束方式为"在两次请求之间"（正常完成 / 工具执行间隙取消） |
| `usage_complete=false` | 存在以下任一：`RunCancelled` 发生在**模型请求在途**时（该请求用量不可得）；provider 未返回 usage；进程被硬杀导致状态丢失 |
| `usage_gap_reason` | 枚举：`in_flight_request_aborted` / `provider_no_usage` / `process_killed` |

**怎么知道取消发生在"模型请求在途"还是"工具间隙"**：由事件流判定 —— 我们已在用 `event_stream_handler`，在 `ModelRequest` 事件与 `FunctionToolCallEvent/FunctionToolResultEvent` 上维护一个进程内微状态机（`current_phase ∈ {idle, model_request, tool_exec}`），取消时取该相位写入 gap reason。**不猜，按事件判**。

#### 2.5.3 单次增量 vs 会话累计（避免重复计数）
| 概念 | 定义 | 存法 |
|---|---|---|
| **run 增量** | 这一次 `run_sync` 新产生的用量 | 每次调用（首跑 / resume / 降级 / 文本兜底）**各写一行** `diagnosis_usage_ledger` |
| **会话累计** | 同一 `conversation_id`（或同一报告链）下所有 run 增量之和 | **由 ledger SUM 推导**，不另存冗余字段 |

**关键陷阱**：resume 时我们按官方要求传 `usage=prior`，框架返回的是**累计值**，不是本次增量。→ 规则：
```
framework_cumulative_after  = result.usage / exc.usage
ledger.this_run_delta       = framework_cumulative_after − framework_cumulative_before
```
`cumulative_before` 取自上次落库的 `framework_cumulative`。**会话累计只认 SUM(ledger.delta)**，绝不再把框架累计值当增量累加一遍（这是最容易出的重复统计 bug，写单测锁死）。

#### 2.5.4 预算：覆盖"不完整用量"与"并发请求"
**记账公式**（判定用）：
```
会话已占用 = SUM(已结算 delta) + SUM(在途预留 reserve)
判定：会话已占用 + 本次预留 ≤ 会话预算  否则拒绝新提交
```
| 要点 | 做法 |
|---|---|
| **不完整用量** | 结算时若 `usage_complete=false`，**按保守上界结算**（取该 run 已测得的最大单请求用量作为在途请求的估计值），标记为"估算部分"，**不允许出现"取消即免费"** |
| **并发请求** | 提交时先**原子预留**（`INSERT … ON CONFLICT DO UPDATE SET reserved = reserved + :r`，事务内比较上限），避免 N 个并发请求各自读到"未超限"而合计超额；run 结束后**结算**（`reserved -= r; settled += actual`） |
| **预留额度** | `diagnosis_budget_reserve_tokens`（默认 = 单次诊断 P95 × 1.2，可配），超时未结算由 reaper 释放 |
| **两道限额** | ①框架 `UsageLimits(cost_limit, total_tokens_limit, request_limit, tool_calls_limit)` 管**单次**；②会话预算管**累计**。二者与关系 |
| **窗口** | 会话预算默认**滚动窗口**（`diagnosis_session_window_seconds`），不是按天归零（按天会让"跨零点"成为绕过口子） |

**展示口径**：界面显示"**≈ ¥X（估算）**"，完整时前缀 `≈` 可换成实测标记；`usage_complete=false` 时显示"**含估算部分**"并可展开原因。

## 附录 A：实测修正（第一批「停止」实施中发现的真实约束）

这三条都是**真机验收**才暴露的，直接改了实现，写在这里避免后人重踩：

1. **`event_stream_handler` 会把 run 切到流式路径**。传了进度回调后，`run_sync` 走流式；
   此时若模型只有同步函数（无 `stream_function`），`cancellation_token` **观测不到取消**。
   线上模型（deepseek / OpenAI 兼容）本身是流式，因此生产无碍；**测试必须用流式模型**。
   另外 `CancellationToken.cancelled` 是**属性**不是方法。

2. **pydantic-ai 2.55 禁止在同步工具里嵌套 `run_sync`**（防死锁，报
   "cannot be used inside a synchronous tool … Make the function `async def`"）。
   我们的取证子代理 / 专家子代理因此**从 `run_sync` 改为 async + `await agent.run(...)`**
   （`investigate`、`consult_specialists`、`run_specialists` 全部 async 化，
   并统一透传 `cancellation_token`）。这是升级发现的**真实回归**，不是本次新增功能。

3. **uvicorn 的关停顺序是"停止接收 → 等 BackgroundTask 跑完 → 关闭 lifespan"**。
   而我们要取消的正是它在等的那个 BackgroundTask —— 只在 lifespan 的 finally 里取消**太晚**
   （实测 SIGTERM 后诊断还继续跑了 30s+）。改为**链式信号处理器**：
   先调用 uvicorn 原处理器（置退出标志），再**同步**做有界清理（取消 token → 最多等 5s 落库 →
   未落库的自己写 `cancelled` + `resumable=false`）。守护线程会被解释器直接掐掉，
   因此这里选择同步执行。配套 `--timeout-graceful-shutdown 20` 给 uvicorn 一个上界。

4. **"用量不完整"是常态而非例外**：真实取消（落在模型请求在途）后
   `RunCancelled.usage` 的各字段为 `None` → 落库为 0，但**必须标 `usage_complete=false`**，
   否则会变成"取消即免费"的预算漏洞（第一批的后续阶段实现）。
