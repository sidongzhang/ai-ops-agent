# 诊断中断与成本控制设计

> 一句话：给用户"停止"的能力，**同时**保证中断真的省钱、中断后的上下文不白扔。
> 状态：**计划（待评审）**，未开始实现。

---

## 1. 目标与非目标

### 目标
1. 用户发起诊断后，**随时可中断**（控制台 + SVOM 浮窗 + 外部 OpenAPI）。
2. 中断**必须真正止损**：不再发下一轮 LLM 请求、不再重复取证。
3. 中断后的**上下文可续用**：对话窗口保留部分证据，后续提问/「继续」复用已采集结果。
4. 给需求方可展示的**成本账**：本次中断花了多少 token、复用了多少条证据。

### 非目标（本期不做）
- 不做"边生成边看"的真流式输出（现在是轮询 + 每步落库，够用）。
- 不做多轮对话的自动摘要重写（已有 `ProcessHistory`，不重复造）。
- 不改写操作审批链路（中断只针对**只读诊断**；已批准的执行动作不回滚）。

## 2. 现状与问题

### 2.1 执行链路（读代码得到的事实）
```
POST /systems/{id}/diagnose            api/diagnose.py
  └─ start_diagnosis()                 建 report(status=running)，立即返回
  └─ BackgroundTasks: complete_diagnosis_report()
       └─ diagnose_system()            services/diagnostics/service.py
            └─ diagnose_with_details() agent/diagnostics/runner.py
                 └─ diagnose_agent.run_sync(question, event_stream_handler=…)
                      ├─ 每步工具调用 → _progress_recorder 写 report.evidence
                      └─ _memoized 进程内 tool_cache 去重
前端/外部：轮询 GET /diagnosis-reports/{id}
```
- 终止状态只有 `running | success | failed`（`_finalize_report` 只认 `running` 才写）。

### 2.2 成本从哪来（这是设计的锚点）
一次诊断的开销 ≈ **轮数 × 单轮上下文**，且**每轮都要重发整段上下文**（system prompt + 历史 + 已采集证据），所以成本随轮数近似**二次增长**。

> 实测参考：一次"贴图诊断" total_tokens ≈ **33k**，工具步 7~12 步。

结论：**省 token 的主战场是"减少轮数"，不是"缩小单次请求"**。
因此中断的价值 = **砍掉后续所有轮**；而"中断后重问"若不复用证据，就等于把已花的钱再花一遍 —— 这是本设计最要解决的问题。

### 2.3 现有问题清单
| # | 问题 | 后果 |
|---|---|---|
| P1 | 无取消入口 | 用户改主意只能干等，烧满 `UsageLimits` 上限 |
| P2 | 无取消字段/状态 | 前端无法区分"失败"与"用户中断" |
| P3 | `tool_cache` 进程内、诊断结束即销毁 | **中断后重问 = 全部重查 = 重复烧 token** |
| P4 | 只有单次诊断限额，无会话级预算 | "取消→重问"可无限循环，绕过限额 |
| P5 | 中断那一轮若作为"上一轮"注入（`follow_up_report_id`） | 模型可能把**半截结论当定论**（同"记忆污染"风险） |

## 3. 设计总览

```
用户点「停止」
  → POST /systems/{id}/diagnosis-reports/{rid}/cancel
      ├─ 幂等：置 cancel_requested_at（只置标志，不改状态）
      └─ 返回 202
  运行中的 agent（协作式取消点，见 3.2）发现标志
      → 抛 OperationCancelled → run_sync 退出
      → _finalize_report(status="cancelled", tokens_used=…, 证据快照)
      → 落库 evidence_cache（供后续复用）
前端轮询到 status=cancelled
      → 气泡显示「已中断 · 已采集 N 步 · 消耗 X tokens」，给出「继续 / 忽略」
```

**为什么标志位与终态分离**：终态要由**跑代码的那一方**写，才能带上真实 token 与完整证据；API 只置标志（幂等、无竞态）。进程被杀导致标志无人消费时，由兜底 reaper 收尸（3.5）。

### 3.1 状态机
```
running ──success──▶ success
    ├────failed────▶ failed
    ├──cancel_requested_at 置位 ──(agent 观察到)──▶ cancelled
    └──(进程死/超时 N 分钟)────reaper────────────────▶ cancelled | failed
```
新增：`cancelled`。`_finalize_report` 增加 `cancelled` 分支。
**中断不写长期记忆**（`save_memory` 仍只在 success 走），但**保留部分证据**供下一轮上下文用。

### 3.2 取消点（协作式，工具边界）
只读诊断，所以**不打断在途工具**（避免半执行/半返回），只在**边界**取消：

| 取消点 | 位置 | 作用 |
|---|---|---|
| C1 每步事件 | `runner._build_event_stream_handler` 的 `async handler`（每个事件被调用） | **主力**：在下一轮 LLM 请求前退出，砍掉后续所有轮 |
| C2 工具入口 | `tools._memoized` wrapper 开头 | 兜底：工具开始前再查一次 |
| C3 请求前 | `runner` 在两处 `run_sync` 调用前 | 极端兜底（重试/降级路径） |

检查代价：**读进程内 `CancelToken`（带 2s TTL 的内存缓存）**，避免每步打 DB。
多实例/Celery 部署时同源生效（DB 标志位 + 短暂缓存）。

### 3.3 成本控制：四道闸（按收益排序）
1. **砍后续轮**（C1）：中断最多多花"在途那一轮"，绝不再发下一轮。**这是主要收益。**
2. **证据跨轮复用**（新表 `evidence_cache`）：
   - key = `(org_id, system_id, tool, args_hash)`，value = 工具输出（已截断）+ `observed_at` + `hit_count`。
   - 新诊断启动时**预填** `deps.tool_cache`（只填未过期的），复用既有 `_memoized` 语义。
   - **新鲜度分档 TTL**（可配）：
     | 类别 | TTL | 例 |
     |---|---|---|
     | 健康/容器状态/日志 | 3 min | `list_services`、`check_service`、`read_logs` |
     | 指标/中间件只读 | 5 min | `query_prometheus`、`run_kafka_command` |
     | 业务数据集/归档 | 15 min | `query_business_dataset`、`read_archive_file` |
     | 拓扑/变更/知识库 | 60 min | `get_service_topology`、`recent_changes`、`search_knowledge_base` |
   - 命中时工具返回**显式标注**："（复用 {observed_at} 的取证结果，若已过时请加参数强制刷新）"——沿用现有 `_memoized` 的"已查过，别重复调用"提示风格。
   - **多租户隔离**：key 必带 `org_id`；跨租户绝不命中。
   - **隐私**：只存已截断的工具输出（沿用 `NESTED_OUTPUT_LIMIT` 截断），按 TTL 自动清理，不做长期留存。
3. **会话级预算**（新）：按 `(org_id, user_id, system_id)` 在**时间窗**内累计 tokens/请求数。
   - 目的：堵住"取消→重问→取消→重问"绕过单次 `UsageLimits` 的口子。
   - 超限 → 直接拒绝并返回明确提示（而不是继续烧）。
   - 与 `UsageLimits` 是**与关系**（两道都要过）。
4. **去重与防抖**：同一 `(系统, 用户, 问题)` 在 60s 内重复提交 → 返回**已有 report**（不新建），前端直接续看。

### 3.4 中断后的上下文（"终端上下文怎么办"）
| 问题 | 方案 |
|---|---|
| 那一轮消息显示什么？ | 保留为 `cancelled` 气泡：`已采集 N 步证据` + 已得的部分结论（若有）+ `消耗 X tokens`；配「继续」「忽略」两个动作 |
| 「继续」怎么做？ | 同问题重跑，**带 `follow_up_report_id=被中断的 report`**，且 `evidence_cache` 预填 → 成本 ≈ 1~2 轮（预期 ≤ 首次的 30%） |
| 「忽略」怎么做？ | 仅从当前窗口移除该气泡，不动服务端证据缓存 |
| 后续新提问会不会被半截结论带偏？ | 注入上下文时**显式标注**：`⚠️ 上一轮被用户中断，仅完成部分取证，其结论不完整、不可作为定论`；并把"已采集证据清单"单独列出供复用 |
| 长期记忆会不会被污染？ | **中断不写记忆**（保持现状：仅 success 写） |
| 上下文膨胀？ | 继续复用的 `ProcessHistory` 压缩 + 只注入"证据摘要"而非全部原始输出（沿用 `iter_tool_events` 的紧凑载荷） |

### 3.5 兜底 reaper
`running` 超过 N 分钟（默认 10，与前端轮询超时一致）且无人推进 → 标 `cancelled`，错误信息"执行方已失联"。
时机：Celery beat 已有的定时任务里顺手做（`services/monitoring/scheduled.py` 的循环，或新增一个 beat 任务）。

## 4. 数据与接口变更

### 4.1 表结构（迁移 `e3f4a5b6c7d8`）
```sql
-- diagnosis_reports 增列
cancel_requested_at  timestamptz NULL
cancelled_at         timestamptz NULL
tokens_at_cancel     int NOT NULL DEFAULT 0      -- 便于"中断只花了 X"展示与对账

-- 新表：证据复用缓存
CREATE TABLE evidence_cache (
  id serial PRIMARY KEY,
  org_id int NOT NULL,
  system_id int NOT NULL,
  tool varchar(64) NOT NULL,
  args_hash varchar(64) NOT NULL,
  args_preview varchar(500) NOT NULL DEFAULT '',   -- 便于排查，不含敏感大字段
  output text NOT NULL,
  evidence_class varchar(32) NOT NULL,             -- health/metrics/business/static → 决定 TTL
  observed_at timestamptz NOT NULL,
  hit_count int NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (org_id, system_id, tool, args_hash)
);
CREATE INDEX ix_evidence_cache_lookup ON evidence_cache (system_id, tool, observed_at);
```
> SQLite 兜底列同步加入 `core/database.py::_SQLITE_REQUIRED_COLUMNS`（沿用现有做法）。

### 4.2 接口
| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/systems/{id}/diagnosis-reports/{rid}/cancel` | 幂等置标志；返回 `{status:"cancelling"}`；非 running → 200 无操作 |
| `POST` | `/openapi/v1/diagnoses/{rid}/cancel` | 外部链路（ALGP/SVOM）同能力 |
| `GET` | `/systems/{id}/diagnosis-reports/{rid}` | 响应新增 `cancelled_at`、`tokens_at_cancel`、`reusable_evidence_count` |
| `POST` | `/systems/{id}/diagnose` | 请求体新增 `force_refresh: bool=false`（忽略证据缓存重新取证）、`resume_report_id`（语义同 `follow_up_report_id` 但带"中断续跑"标记） |

### 4.3 配置（`core/config.py`）
```python
diagnosis_cancel_poll_ttl: float = 2.0        # 取消标志内存缓存 TTL（秒）
evidence_cache_enabled: bool = True
evidence_cache_ttl: dict = {...}              # 分档 TTL（见 3.3）
diagnosis_session_token_budget: int = 300000  # 会话级预算（10 分钟窗口）
diagnosis_session_window_seconds: int = 600
diagnosis_stale_running_minutes: int = 10     # reaper 阈值
```

### 4.4 前端
- **AIOps 控制台**（`features/diagnostics/`）：running 气泡旁加「停止」；`useDiagnosisChat` 增 `cancel()`；终态渲染 `cancelled` 卡片（证据 + `继续/忽略`）。
- **SVOM 浮窗**（`AiopsAssistant.vue`）：同上；`MessageCenterApi` 增 `cancelDiagnosis(id)`；ALGP 增加转发路由（参照现有 diagnoses 转发）。
- 轮询间隔 2.5s 保持不变（中断到生效 ≤ 1 个工具步，通常 <3s）。

## 5. 风险与对策
| 风险 | 对策 |
|---|---|
| 取消"卡"在长 LLM 请求里 | 只在工具边界取消（不 abort 在途请求）；**收益仍成立**（后续轮全砍）；P3 再评估 abort |
| 工具已发出（远程采集器） | 不中断在途工具；只读语义下无副作用 |
| DB 轮询拖慢每步 | 内存缓存 2s TTL，正常情况下 0 次 DB 查询 |
| 证据缓存导致"旧数据当新数据" | 分档 TTL + 命中时**显式标注观测时间** + `force_refresh` 开关 |
| 多租户串数据 | key 含 `org_id`，检索必带租户过滤；测试覆盖 |
| 前端连点取消 | 后端幂等；前端置按钮为 loading |
| 取消绕开限额 | 会话级预算（3.3-3），与 `UsageLimits` 双重生效 |
| 进程死亡导致 running 永久挂起 | reaper（3.5） |

## 7. 验收标准（可量化，写成本期的测试）
1. **中断不再烧**：中断后 1 分钟，`total_tokens` 不再增长；`tokens_at_cancel` ≤ 已完成轮数 × 单轮上限。
2. **中断及时**：点击到 `status=cancelled` ≤ 3s 或 1 个工具步。
3. **复用有效**：中断→「继续」同问题的总 token ≤ 首次的 **30%**；证据复用命中率 ≥ **70%**。
4. **预算兜底**：连续"取消+重问"在窗口内无法越过会话预算（超限被拒）。
5. **租户隔离**：A 组织的证据缓存绝不出现在 B 组织的诊断里（单测覆盖）。
6. **不污染记忆**：中断的诊断不产生 `knowledge_memories` 记录。
7. **兼容**：不传新参数时行为与现状一致（旧前端/旧 ALGP 不受影响）。

## 8. 测试计划
- 单测：取消标志读取（含缓存/TTL/DB 失败降级）· `_finalize_report(cancelled)` · 证据缓存读写与 TTL 过期 · 会话预算窗口计算 · 分档 TTL 归类。
- 集成：起一个"可控慢工具"（本地 sleep 工具）→ 中断 → 断言轮数/token 不再增长、状态为 `cancelled`。
- 端到端：控制台 + SVOM 浮窗各点一次「停止」；再点「继续」验证复用与成本。
- 门禁：`evals` 冒烟不受影响（新增用例走同一 harness）。

## 9. 待拍板（实现前需要你定的点）
1. **会话级预算的具体额度**：默认 10 分钟 / 30 万 token 可以吗？（按"3 次完整诊断"估的）
2. **「继续」的默认行为**：默认复用证据（省钱）还是默认强制刷新（更新鲜）？我倾向**默认复用 + 一键刷新**。
3. **TTL 分档**：3/5/15/60 分钟这四档是否合适？（越短越新鲜、越长越省）
4. **`cancelled` 的中文呈现**：主叫"已中断"还是"已停止"？（影响前端文案与消息中心筛选项）
5. **是否要 P3**（abort 在途请求）：收益不确定（取决于 provider 是否对已取消请求计费），但实现成本中等。
