# 归档文件问答能力 — 工具设计方案

> 目标：用户查出"触发/爆发"后，可以继续追问——归档在哪、里面有哪些文件、每个文件是什么、做个分析；
> agent 能给出**文件路径**，必要时把**文件本身**回传。

---

## 1. 先说结论（一句话）

这不是"harness"，是给运维 agent **增加几个只读工具（tool use）**；而且 **ALGP 后端已经把一半能力做好了**，
我们主要是把它**接到 agent**，并补上"文件类型解释 + 文件回传"。

---

## 2. 现状摸底（重要）

### 2.1 ALGP 后端已有能力

`algp-datacenter/…/DataSearchController.java`：

| 接口 | 作用 |
|---|---|
| `GET /dataManagement/triggerBurst` | 触发/爆发列表，含 `archiveDir`(归档路径)、`archiveTcatId`(归档目录名)、`archiveFileCount`、ra/dec/clas 等 |
| `GET /dataManagement/triggerBurst/archiveFiles?tcatId=&modeCode=` | 解析归档目录并**列出文件** |
| `GET …/archiveFiles/download` | 下载某个归档文件 |
| `GET …/archiveFiles/content` | 读取文件内容（预览） |

### 2.2 "映射"到底是什么

**不是一张关系映射表**，而是**字典配置 + 由 tcatId 推导**：

- 配置项（`SYS_DICT` / `SYS_DICT_ITEM`，dictCode = `multi_analysis_path`）：
  - `archive_base_path`：归档根目录
  - `archive_path_pattern`：默认 `${basePath}/${YYYY}/${MM}/${archiveTcatId}`
- 解析链路（`buildArchiveLocation`）：
  `tcatId(+modeCode)` → `modeCode`（查 `general_run_tcat` JOIN `general_analysis_run`）→ `archiveTcatId`
  → `archiveDir`（按 pattern 计算）

### 2.3 文件类型（后端已内建识别）

`archiveResultKind(fileName)` 只认这 4 类，且列目录时**每类取一个代表文件**：

| 后缀 | 类型 |
|---|---|
| `.tcat` | 候选触发记录 |
| `.pdf` | 分析报告 |
| `_loc.fits` | 联合**定位**结果 |
| `_joint.fits` | 联合**分析**结果 |

### 2.4 ⚠️ 本机现状：没有真实归档文件

当前配置指向 mock 的 **Windows 路径**：

```
archive_base_path    = D:/Develop/algp-mock/jointAnalysis
archive_path_pattern = ${basePath}/${YYYY}/${MM}/${archiveTcatId}
```

本机（macOS）不存在该目录，也找不到任何 `_joint.fits / _loc.fits / *.tcat`。
👉 **要本地演示"文件内容/回传"，必须先造一批样例归档文件**，并把字典指向本地可访问目录。

### 2.5 数据库里已有「路径 + 文件索引」（重要发现）

| 来源 | 说明 |
|---|---|
| `general_run_tcat.archive_dir` | 每条 TCat 的归档目录（41/93 行有值） |
| `artifact_record` | **文件级索引，5254 行**，覆盖 **164 个 t_cat_id**；字段含 `t_cat_id / file_name / file_type / file_size / file_path / archive_dir / stage / service_id / run_id / created_time` |

例（`tn260717_120003_gbm`，14 个文件 / 3 阶段）：`search`→`*.tcat`；`cut`→`*_CUT_*.fits`（GBM/GECAM/SVOM 各载荷）；`analysis`→`result_*_loc.fits`、`result_*_joint.fits`、`location_*.json`、`catalog_match_*.json`、`grb_analysis_*.json`、`result_*.pdf`。
全库类型分布：json 2072 / fits 1810 / pdf 1293 / tcat 41 / png 1 / txt 1。

**结论：路径、文件名、类型、大小、阶段、产出来源，DB 里全有**（路径是 mock 的 `D:\Develop\algp-mock\…`，本机无实体文件）。

## 3. 架构约束

- ALGP 是**远程系统**：agent 在平台侧，靠**采集器出站通道**通信。文件访问**必须由采集器在 ALGP 机器上执行**
  （沿用现有 `run_readonly_query` / `fetch_logs` 的模式）。
- 归档目录做**白名单根**、**只读**、**限制大小/条数**、**全程审计**。绝不让 agent 任意读文件系统。
- 不引入任何"agent 自动生成工具"的机制；只加**固定、可审计**的工具。

---

## 4. 要新增的工具

> **好消息（见 2.5）**：仅靠 `artifact_record` 单表，**P0 可以先不碰文件系统**——把它做成只读数据集，
> agent 用现有的 `query_business_dataset` 就能答"归档目录 + 文件清单 + 类型/大小/阶段/来源"。
> 采集器侧的文件工具（读内容 / 回传）放到 **P0.5 / P1 / P2**。

### P0 — 让 agent"看得到"

| 工具 | 入参 | 出参 | 说明 |
|---|---|---|---|
| `resolve_archive` | `tcatId`, `modeCode?` | `{archiveDir, archiveTcatId, modeCode, fileCount, ra/dec/clas}` | 解析归档路径与天区元数据 |
| `list_archive_files` | `tcatId`, `modeCode?` | `[{name, path, size, mtime, kind}]` | 列目录（可按 kind 过滤） |
| `read_archive_file` | `tcatId`, `fileName`, `filePath?`, `maxBytes?` | 文本串 / FITS 头摘要 | 文本直读；二进制给**头部摘要**（FITS header 关键字），限制字节数 |

### P1 — 让它"讲得清"

- 建立 **文件类型 → 中文说明** 映射（见 2.3），随数据集目录注入 prompt；
- agent 结合文件名 + FITS 头/文本摘要，**解释每个文件是什么**并做分析；
- 说明里标注"依据文件路径"，可追溯。

### P2 — 让它"发得回"

| 工具 | 入参 | 出参 | 说明 |
|---|---|---|---|
| `fetch_archive_file` | `tcatId`, `fileName`, `filePath?` | 平台侧文件引用（附件/下载链接） | 需一条**文件回传通道**（采集器→平台）+ 前端展示。最重、最后做 |

## 5. 采集器侧实现要点

新增采集器命令（`collector/ws_client.py` 分发）：

```
resolve_archive      → 返回归档目录 + 元数据
list_archive_files   → 列目录（含 kind 分类）
read_archive_file    → 读文本 / FITS 头摘要
fetch_archive_file   → 回传文件（P2）
```

路径解析两种实现方式：

- **方案 A**：采集器直接调 ALGP 后端接口（`/triggerBurst/archiveFiles`）。
  - 缺点：需要采集器携带 ALGP 的鉴权/会话，耦合重。
- **方案 B（推荐）**：采集器**只读**直接访问文件系统 + 数据库：
  1. 复用现有只读 DB 连接查 `SYS_DICT`（`archive_base_path` / `archive_path_pattern`）与 `general_run_tcat`；
  2. 用与后端一致的规则算出 `archiveDir`；
  3. 白名单校验（路径必须落在 `archive_base_path` 下）后列目录/读文件。
  - 优点：不依赖 ALGP Web 鉴权，只读、可审计、与现有只读策略一致。

**FITS 头**：只读前若干 KB 解析 `KEY = value` 头关键字即可（简单解析，无需 astropy）。

**安全**：`realpath` 前缀校验、单文件/总量字节上限、条目数上限、全部写审计。

## 6. "每个文件是什么" 的解释策略

1. **规则优先（稳）**：先按 2.3 的 kind 给基础说明（如 `_joint.fits` = 联合分析结果）。
2. **LLM 补充**：结合 FITS 头（TELESCOP/INSTRUME/OBJECT/TARGRA/DATE-OBS 等）与文本摘要，补充"这个文件在这次观测里是什么角色"。
3. 结论里**引用具体文件路径**，避免空泛。

## 7. 本地演示前置

- **P0（元数据）无需任何前置**：路径/文件清单来自 `artifact_record`，DB 里已有。
- **P0.5 起（读内容 / 回传）才需要实体文件**：
  - 按 `${basePath}/${YYYY}/${MM}/${archiveTcatId}` 结构造样例文件（`.tcat` / `*_loc.fits` / `*_joint.fits` / `.pdf` / `.json`）；FITS 用最小合规头文件即可（可脚本生成）。
  - 把字典 `multi_analysis_path.archive_base_path` 指向**本地可访问目录**（如 `~/Desktop/school/algp-mock/jointAnalysis`）。
  - 真机部署时则指向 ALGP 服务器上真实的归档根。
- `artifact_record.file_path` 存的是 mock 的 Windows 路径；若要按它读实体文件，需把该列一并改到本地/真实根。

## 9. 与 harness 的关系

无关。本项目 harness（`evals/`）是"评 agent 的脚手架"；本需求是"给 agent 加工具"，
属于 agent 的**工具/能力扩展**，不改评测框架。
