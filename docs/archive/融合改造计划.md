# 智能运维平台融合改造计划

## 1. 改造目标

本次改造的目标是：保留当前项目已经做得好的平台能力，同时吸收《智能运维机器人设计方案》中更完整的业务接入、消息加工、审计和策略能力，最终形成一个“能接入、能监控、能告警、能分析、能建议、能审批执行、能追溯”的智能运维平台。

本计划不以技术堆栈为中心，只关注三个结果：

- 功能是否真的可用：用户和业务系统能不能完成完整运维闭环。
- 效率是否真的提升：是否减少人工切换系统、人工分析和重复通知。
- 仓库是否保持干净：无用代码、旧入口、废弃配置和重复实现要及时清理。

## 当前执行进度

截至当前版本，融合改造已经完成以下可用闭环：

- 已完成：统一消息中心、消息状态管理、网页内提醒、飞书和邮件配置、渠道发送结果记录。
- 已完成：业务系统 Token、权限范围、过期和禁用、开放告警/健康/日报/月报接口、重复请求拦截。
- 已完成：规则化告警分析与建议；AI 不可用时仍能生成基础建议。
- 已完成：首批诊断模板并扩展到 8 类，支持按系统启停；诊断回答显示模板、证据来源和耗时。
- 已完成：只读数据库配置、连接测试、安全查询、超时与行数限制、敏感字段脱敏。
- 已完成：消息、外部接入、诊断、模板设置、审批和执行结果审计。
- 已完成：服务先保存为草稿，测试报告持久留存；后端强制测试通过后才能启用，修改配置后必须重新测试。
- 已完成：容器重启后自动回查服务是否恢复，失败时停止并提示人工处理。
- 已完成：外部通知渠道可多选并行发送；临时失败自动重试，消息中心可集中筛选和手动重试失败通知。
- 已完成：Prometheus 地址识别、PromQL 合法性、指标存在性和指标状态校验，失败时给出明确原因。
- 已完成：效率分析面板，支持按时间和系统查看告警解决率、处理时间、诊断质量、通知可靠性和拦截效果。
- 已完成：“任务一直处理中”通用专项闭环，可配置任务字段与卡住阈值，联合查询状态分布、卡住样例、Worker 健康和异常日志，并把证据带入审批修复与执行后回查。

## 2. 保留当前项目的优势

当前项目已经具备一套不错的基础，后续不要推倒重来，应作为融合后的主干继续演进。

保留能力：

- 多租户控制台：保留组织、用户、登录、系统列表、系统详情等能力。
- 服务注册：保留当前系统与服务注册方式，继续支持 HTTP、TCP、Prometheus、Redis、Kafka、MySQL 等服务。
- 健康探测：保留直接探测和 collector 内网探测两种模式。
- 监控面板：保留系统资源、Redis、Kafka、MySQL、HTTP 服务状态展示。
- AI 诊断：保留当前对话式诊断、知识库检索、指标查询和日志查询能力。
- 审批修复：保留当前“AI 提建议 -> 用户批准 -> 执行 -> 返回结果”的闭环。
- 飞书集成：保留飞书主动告警和飞书消息触发诊断能力。
- 安全基础：保留敏感字段加密、API 响应掩码、租户隔离和权限控制。
- 前端体验：保留当前系统详情四个区域：概览、监控、诊断、配置。

## 3. 新增方案中的优势能力

融合方案重点补齐当前缺失的产品能力，不为了“看起来完整”增加用户用不到的复杂功能。

### 3.1 统一消息中心

新增一个统一消息中心，用来集中保存告警、诊断建议、日报、月报、年报、操作结果等消息。

需要实现的功能：

- 平台内可以查看所有系统消息。
- 每个系统可以查看自己的消息列表。
- 消息支持未读、已读、已确认、已解决状态。
- 告警消息必须包含问题位置、影响范围、原因分析、建议措施。
- 飞书、邮件、网页内提醒都从统一消息中心发出，避免各处重复拼消息。

验收标准：

- 某个服务异常后，平台内能看到一条告警消息。
- 同一条告警能同时推送到飞书、邮件或网页提醒。
- 管理员可以确认告警、标记解决。
- 业务系统可以只查询属于自己的消息。

### 3.2 业务系统开放接入

新增开放接口，让外部业务系统可以主动把告警、健康状态、运行报告提交给平台。

需要实现的功能：

- 每个业务系统可以申请独立接入 Token。
- Token 可以禁用、轮换、设置过期时间和允许调用范围。
- 业务系统可以上报告警、健康状态、日报、月报。
- 平台收到数据后，可以选择直接转发，也可以先进行智能加工。
- 同一个请求重复提交时，不能重复发送消息。

验收标准：

- 外部系统拿 Token 后，可以成功提交一条告警。
- Token 失效、权限不够、系统不匹配时必须拒绝请求。
- 重复请求不会重复创建消息或重复通知。
- 平台能返回处理状态，业务系统能查询结果。

### 3.3 告警自动分析与建议

当前告警主要告诉用户“哪个服务异常”，后续要升级为“哪里异常、为什么可能异常、下一步怎么处理”。

需要实现的功能：

- 告警产生后，自动补充最近健康状态、指标、日志和知识库内容。
- AI 生成简短诊断和处理建议。
- 建议要分成低风险检查、需要确认的操作、必须人工处理的操作。
- 对高风险操作只给建议，不自动执行。

验收标准：

- 告警内容不只是“Redis 异常”，而是能说明检测依据和建议动作。
- 用户看到告警后，不需要再手动打开多个页面找基础信息。
- AI 建议中必须写明证据来源，例如健康检查、Prometheus 指标、日志或知识库。

### 3.4 邮件与网页内提醒

保留飞书，同时新增邮件和网页内提醒。

需要实现的功能：

- 通知渠道可以按系统配置。
- 支持飞书、邮件、网页内提醒。
- 支持测试通知。
- 支持通知发送结果记录。
- 通知失败要能重试或标记失败，不能静默丢失。

验收标准：

- 管理员可以为一个系统配置多个通知渠道。
- 测试通知能明确返回成功或失败原因。
- 告警触发后，消息中心能看到每个渠道的发送结果。

### 3.5 可配置诊断模板

保留当前 AI 对话能力，但把常见问题的排查步骤沉淀成模板，减少 AI 自由发挥，提高稳定性和效率。

需要实现的功能：

- 常见问题可以配置诊断模板。
- 模板中定义排查步骤、需要调用的数据、输出要求。
- AI 根据用户问题选择模板，再按模板组织诊断。
- 模板执行结果要保存，便于复盘。

第一批模板：

- 服务不可达。
- Redis 内存或连接异常。
- Kafka 消费积压。
- MySQL 连接数、QPS、慢查询异常。
- HTTP 接口健康检查失败。

验收标准：

- 用户问“Kafka 为什么堆积”，系统能按固定步骤检查 Kafka 状态、消费组、指标和日志。
- 相同问题多次诊断时，结构稳定，不出现每次都完全不同的排查路径。

### 3.6 只读数据分析

新增安全的数据分析能力，让管理员能问“某些业务数据有没有到达”“数量是否异常”等问题。

需要实现的功能：

- 只允许查询，不允许修改数据。
- 查询必须有超时和最大返回行数限制。
- 敏感字段要脱敏。
- AI 回答时必须说明查询了哪些数据。

验收标准：

- 管理员可以问“今天有没有新数据到达”，系统能查库并给出统计结果。
- 系统必须拒绝删除、修改、清空、建表等危险操作。
- 查询慢或失败时，要给出明确原因，不拖垮平台。

### 3.7 全链路审计

新增统一审计能力，记录一次诊断和操作从开始到结束的全过程。

需要实现的功能：

- 记录用户问题。
- 记录命中的诊断模板。
- 记录调用了哪些工具。
- 记录工具输入、输出、耗时和成功失败。
- 记录 AI 生成的结论和建议。
- 记录用户是否批准、谁批准、执行结果是什么。
- 记录通知发送结果。

验收标准：

- 任意一次诊断都能追溯“为什么得出这个结论”。
- 任意一次操作都能追溯“谁发起、谁批准、执行了什么、结果如何”。
- 审计记录可以按系统、用户、时间范围查询。

### 3.8 执行后回查

自动执行不等于业务恢复。后续每个恢复操作都必须回查结果。

需要实现的功能：

- 执行前记录当前状态。
- 执行后等待一段时间再检查健康、指标或日志。
- 恢复成功则关闭操作。
- 恢复失败则停止继续自动操作，并生成给人工的恢复建议。

验收标准：

- 重启服务后，系统会自动确认服务是否恢复。
- 如果没有恢复，系统不会反复重启，而是提示人工检查方向。

### 3.9 探针测试后启用

服务和探针配置必须先测试，再启用，减少误报和漏报。

需要实现的功能：

- 新增配置时先作为草稿。
- 点击测试后返回测试报告。
- 测试通过后才能启用正式监控。
- 测试失败要给出原因和建议。

验收标准：

- 错误的健康检查地址不能直接进入正式监控。
- 用户能看到失败原因，例如 404、超时、连接失败、指标不存在。

## 4. 分阶段改造计划

执行时需要额外遵守三条优化原则：

- 告警不要单独再建一套和消息中心重复的状态。告警是统一消息中心里的一种消息类型。
- 第一阶段不同时做开放接口、邮件、复杂 AI 分析和前端大改。先完成“消息入库、查询、确认、解决、告警接入”，再逐步扩展通知和页面。
- AI 自动分析必须有降级策略。AI 失败时仍然要创建告警消息，并给出规则化建议，不能因为模型不可用影响告警效率。

### 第一阶段：把告警和消息闭环做完整

目标：让用户清楚知道哪里出了问题、为什么可能出问题、下一步怎么做。

交付内容：

- 统一消息中心。
- 告警记录和状态管理。
- 网页内提醒。
- 邮件通知。
- 告警自动诊断建议。
- 通知发送结果记录。

验收结果：

- 服务异常后，平台能自动生成带建议的告警消息。
- 管理员能在网页内看到、确认、解决告警。
- 飞书、邮件、网页提醒都能从同一条消息发出。

### 第二阶段：开放接入业务系统

目标：让外部系统可以主动把告警、健康、报告交给平台处理。

交付内容：

- 系统 Token 管理。
- Token 禁用、轮换、过期、权限范围。
- 开放告警接口。
- 开放健康状态接口。
- 开放日报、月报接口。
- 请求去重和处理状态查询。

验收结果：

- 一个外部系统可以通过 Token 提交告警。
- 平台能加工消息并发送通知。
- 分系统可以查询自己的消息。

### 第三阶段：提升诊断稳定性和效率

目标：把常见故障从“临场问 AI”升级为“模板化稳定诊断”。

交付内容：

- 诊断模板管理。
- 常见问题模板。
- 工具调用记录。
- 只读数据库分析。
- 诊断结果证据化展示。

验收结果：

- 常见问题能按固定步骤稳定排查。
- 管理员能问数据是否到达、数量是否异常，并得到可验证答案。
- 诊断结果能显示证据来源。

### 第四阶段：强化审批、策略和执行后回查

目标：让平台敢执行，但不乱执行。

交付内容：

- 操作风险分级。
- 操作确认和审批策略。
- 执行后回查。
- 失败后的人工恢复建议。
- 操作审计查询。

验收结果：

- 低风险检查可以快速执行。
- 中高风险操作必须确认或审批。
- 执行后能判断是否真的恢复。
- 失败后不重复执行危险操作。

### 第五阶段：专项业务场景落地

目标：选择一个真实业务场景做完整演示闭环。

建议场景：

- “任务一直处理中”。

交付内容：

- 业务任务状态查询。
- 流程状态查询。
- Worker 状态查询。
- 日志和指标联合诊断。
- 推荐链路探测、重启 Worker、通知负责人等操作。

验收结果：

- 用户用自然语言提问后，平台能定位问题卡在哪个环节。
- 平台能给出证据和建议操作。
- 需要执行操作时，走确认、审批、执行、回查、审计闭环。

## 5. 效率指标

后续每个阶段都要用效率指标验收，而不是只看功能是否存在。

建议指标：

- 平均发现问题时间：从服务异常到平台生成告警的时间。
- 平均定位时间：从告警产生到给出原因和建议的时间。
- 人工切换次数：处理一个问题需要打开几个外部系统。
- 重复告警率：同一问题是否反复打扰用户。
- 自动补全信息比例：告警中是否自动包含健康、指标、日志、知识库证据。
- 操作闭环率：建议操作是否能进入确认、执行、回查、审计流程。
- 无效配置拦截率：错误探针是否在启用前被发现。

目标：

- 常见故障定位时间明显低于人工排查。
- 管理员处理告警时不需要反复复制粘贴信息。
- 低风险排查动作尽量自动完成。
- 高风险动作必须可控、可审计、可追溯。

## 6. 仓库清理原则

保持仓库整洁是硬要求。每次开发都必须同步清理无用代码。

必须清理：

- 已经没有引用的旧文件。
- 被新实现替代的兼容入口。
- 临时调试脚本。
- 临时数据库文件。
- 过期文档和错误说明。
- 重复的 service、schema、api、component 实现。
- 未使用的前端组件、样式和工具函数。
- 未使用的后端函数、模型、迁移草稿和测试夹具。

不能清理：

- 用户尚未确认废弃的数据迁移。
- 仍被历史数据依赖的表结构。
- 生产配置示例。
- 当前功能还在使用的兼容字段。

清理规则：

- 新增功能前先确认是否已有相似实现，优先复用或改造。
- 删除代码前先全仓搜索引用。
- 删除 API 或字段前确认前端、测试、文档和迁移是否仍依赖。
- 每个阶段结束时做一次仓库清理任务。
- 文档必须跟着代码更新，不能留下过时说明。

## 7. 最终融合后的产品形态

融合完成后，平台应该支持如下完整流程：

```text

业务系统注册
  -> 配置服务、探针、通知和权限
  -> 测试通过后启用监控
  -> 平台持续健康检查和指标采集
  -> 异常时创建统一消息
  -> 自动补充指标、日志、知识库和历史告警
  -> 生成原因分析和处理建议
  -> 通过飞书、邮件、网页提醒用户
  -> 用户在平台内查看证据和建议
  -> 低风险动作快速执行
  -> 中高风险动作确认或审批后执行
  -> 执行后回查恢复效果
  -> 全过程写入审计
  -> 业务系统可查询自己的消息和处理结果

```

最终用户感受到的结果应该是：

- 不需要懂底层技术，也能知道哪个系统哪里出了问题。
- 不需要打开多个平台，也能看到关键证据。
- 不需要自己整理通知内容，平台会自动生成清楚的告警和建议。
- 不担心 AI 乱操作，因为高风险操作必须确认、审批和审计。
- 不担心仓库越写越乱，因为无用代码会随着阶段开发持续清理。
