# 数据模型与迁移 体检

审计对象：`backend/app/models/`（21 个模型文件 / 24 张表）、`backend/migrations/versions/`（28 个 revision，实测 `alembic heads` 为单一 head `a1b2c3d4e5f`）、`backend/app/core/database.py`、`backend/migrations/env.py`、`deploy/docker-compose.yml`。

## 现状设计

数据层是「SQLModel 声明模型 + Alembic 手写迁移 + Postgres/pgvector 为主、SQLite 为兜底」的三件套。`app/core/database.py:13` 用 `DATABASE_URL` 前缀分叉：SQLite 走 `SQLModel.metadata.create_all` + 一份**手写的补列清单** `_SQLITE_REQUIRED_COLUMNS`（`database.py:15-72`），Postgres 走 `_run_alembic_upgrade()`（`database.py:90-100`），由 FastAPI lifespan 在进程启动时调用（`app/main.py:90`），compose 里又额外跑了一次 `alembic upgrade head`（`deploy/docker-compose.yml:41`）。迁移链是线性单 head（`238f4c603dd8` → … → `a1b2c3d4e5f`，中间 `4b6a8c2d91f0` 合并了 `23452711f18c` / `9e4a8f7e6f31` 两个分支），每个 revision 都带 `downgrade()`。

租户模型是**扁平两级**：`orgs` → `systems`（`systems.id` 是全局主键）→ 其余业务表。绝大多数表冗余存了 `org_id`，但只有一部分带 FK；`systems.id` 全局唯一这一点被有意利用——向量检索只按 `system_id` 过滤即可（`app/services/knowledge/memory.py:256`、`app/agent/diagnostics/knowledge/store.py:397`），`org_id` 在部分查询里只是冗余列。状态机字段（`status` / `validity` / `state`）全部是裸 `AutoString`，**整个仓库没有任何 `CheckConstraint` 或 `Enum`**（已 grep 确认）。pgvector 的两张表（`knowledge_chunks` / `knowledge_index_meta`）只存在于迁移里，不在 SQLModel metadata 中（实测 metadata 24 张表，不含这两张）。

## 做得好的地方

- **单 head 线性迁移链，28/28 都有 `downgrade()`**：`alembic heads` 实测只有 `a1b2c3d4e5f`；`4b6a8c2d91f0:16` 用 `down_revision` 元组正确处理了分支合并，而不是留一个孤儿 head。回滚可用性在同类项目里属于上乘。
- **有意用「派生状态」而不是加列**：`DiagnosisReport.unverified_reason`（`app/models/diagnostics.py:60-81`）把「success 但无工具调用」判定做成读取时计算的 property，注释里写了 206 条历史报告的标定结果（命中 2 / 误报 0）。避免了一次全表迁移，且历史数据立即生效——这是刻意的、有论证的取舍。
- **幂等基础建立在数据库唯一约束上，而不是应用层判断**：resume 的「同一源报告只能继续一次」用**部分唯一索引** `uq_diagnosis_resumed_from` 实现（`diagnostics.py:13-14` + `migrations/versions/a5b6c7d8e9f0_add_resume_link.py:21-27` 的 `postgresql_where`，SQLite 侧镜像在 `database.py:70`）；用量记账的 exactly-once 用 `attempt_id` 唯一索引（`app/models/usage.py:21` + `c7d8e9f0a1b2_pi_lifecycle_ledger.py:11-12`）；预算并发用 `UniqueConstraint(org_id,user_id,system_id,window_started_at)`（`usage.py:48-50` + `f4a5b6c7d8e9:76`）+ `ON CONFLICT` upsert（`usage.py:262-269`）；事件幂等用 `uq_runtime_event_sequence`（`runtime_events.py:11` + `c7d8e9f0a1b2:23`）。并发正确性交给数据库，方向完全正确。
- **迁移幂等/可重入，而不是「假设干净库」**：`9e4a8f7e6f31_controlled_restart_v1.py:21-28,70-88` 用 `sa.inspect` 逐列判断再 `add_column`，`23452711f18c:26-27` 判断表存在才建表，`9e4a8f7e6f31:101-104` 的 `drop_index` 包了 try/except。对已经被手工改过的库更安全。
- **时间戳只用 aware UTC**：`app/models/common.py:5-6` 的 `utcnow()` 返回 `datetime.now(timezone.utc)`；全仓 68 处 `datetime.now(timezone.utc)`，仅 1 处裸 `datetime.now()`（`app/services/data_analysis.py:98`，而且只取 `.date()` 做参数，不落库）。没有把 naive 本地时间写进库的坏习惯。
- **踩过并绕开了 Alembic 的日志副作用坑**：`database.py:96-99` 与 `migrations/env.py:21-22` 用 `config.attributes["configure_logger"]=False` 阻止 `fileConfig(disable_existing_loggers=True)` 在启动迁移后静默禁用 uvicorn/app.* logger。这是非常容易被误判成「线上日志消失」的经典问题，注释也写清了现象。
- **告警消息 → incident 的关联用了具名 FK 约束**：`b8c9d0e1f2a3_add_incidents.py:50` 用 `create_foreign_key("fk_system_messages_incident_id", ...)`，downgrade 里也按名删除（`:57`），不是匿名约束——回滚路径干净。
- **给趋势巡检建了真正的复合索引**：`d2e3f4a5b6c7_add_metric_samples.py:30` 的 `ix_metric_samples_lookup (system_id, metric, observed_at)` 与查询形态（`trend.py:168-180` 按 system+metric+时间倒序）匹配，并且配套了保留期清理 `prune_samples`（`trend.py:196-206`，读 `settings.trend_retention_days`）。多数项目在这类表上只会留一个永不清扫的时间序列表。

## 发现

### [high] `alembic revision --autogenerate` 会生成 DROP 掉 pgvector 表与 `knowledge_memories.embedding` 的迁移，一次性销毁全部 RAG 数据

- **证据**：`migrations/env.py:25` 用 `target_metadata = SQLModel.metadata`，且全文件**没有 `include_object` / `include_name` 过滤钩子**。而实测 `SQLModel.metadata.tables` 只有 24 张表，**不含** `knowledge_chunks` 与 `knowledge_index_meta`——这两张表只由 `migrations/versions/f7a8b9c0d1e2_add_pgvector_knowledge_chunks.py:34,41` 创建。同时 `app/models/knowledge.py:47-48` 明确注释「模型层不声明该列」，而 `migrations/versions/f8b9c0d1e2f3_add_structured_knowledge_memories.py:41` 建了 `embedding Vector(_dim())`、`:49-55` 建了 HNSW 索引。任何一次 autogenerate 都会产出 `op.drop_table('knowledge_chunks')`、`op.drop_table('knowledge_index_meta')`、`op.drop_column('knowledge_memories','embedding')` 与 `op.drop_index('ix_knowledge_memories_embedding')`。附带风险：`_dim()` 在迁移执行时读运行时 `settings.embedding_dim`（`f7a8b9c0d1e2:23-28`、`f8b9c0d1e2f3:20-23`），列类型在首次 upgrade 时就被冻结，而库里没有任何地方校验运行时维度与既有列维度一致。
- **风险**：触发条件是**日常开发动作**（改完模型跑一次 `alembic revision --autogenerate`），不需要任何恶意输入。一旦生成的迁移被 apply，`knowledge_chunks`（全部文档分块与向量）与 `knowledge_memories.embedding`（全部结构化记忆的向量）直接消失，且 `downgrade()` 只能把**空列/空表**加回来——数据不可恢复。改 `EMBEDDING_DIM` 后在新库上重建，会让新旧部署的向量维度不同，插入报 `expected N dimensions`，而老库上该迁移已是 applied 状态、不会重跑，等于永久分叉。
- **业界做法**：Alembic 官方推荐用 `context.configure(include_object=...)` 把「不由本迁移体系管理的对象」（扩展、外部工具建的表、向量列）显式排除；pgvector 生态的常见做法是把向量列连同其维度写进模型（`Column(Vector(1536))`）或把向量迁移隔离到独立 directory + `depends_on`。云原生 SaaS 的等价机制是「schema 由迁移体系独占、外部组件的表放在独立 schema/数据库」，并在 CI 里跑 `alembic check`（Alembic 1.9+）把「模型与库不一致」变成红灯而不是等人工 autogenerate。
- **可采纳性**：easy。改动面只有 `migrations/env.py` 一个函数（约 15 行）：加 `include_object` 对 `knowledge_chunks`、`knowledge_index_meta` 返回 `False`，对 `knowledge_memories.embedding` 及其索引返回 `False`；再把 `embedding_dim` 落进一张 `schema_meta` 表或写成 `alembic` 版本表旁的一行，启动时断言一致。不需要重构，收益是消除一条一次性数据销毁路径。建议同时把 CI 的 `alembic check` 加进来，否则 `include_object` 会被后人误删。
- **建议**：改 `backend/migrations/env.py`，在 `run_migrations_offline/online` 的 `context.configure(...)` 里加 `include_object=_include_object`，白名单式排除上述对象并注释原因（指向 `app/models/knowledge.py:47-48`）。另在 `migrations/versions/` 新增一个只读校验用的启动断言（如 `app/core/database.py:_run_alembic_upgrade` 之后查 `information_schema` 的 `atttypmod` 与 `settings.embedding_dim` 对比，不一致就大声报错而不是静默降级）。预期收益：autogenerate 从「危险操作」变回「可用工具」。

### [high] 「清理诊断历史」删除成功后，完整对话历史 / 工具输出 / 审计内容仍留在库里，且与删对话路径行为不一致

- **证据**：`app/services/diagnostics/reports.py:213-234` 的 `clear_diagnosis_reports` 只删两类行——`DiagnosisJob`（`:227`）和 `DiagnosisReport`（`:229-230`），然后返回 `count`；`app/api/diagnose.py:347-356` 把它包装成 `DELETE /{system_id}/diagnosis-reports` 并回 `{deleted: N}`。**没有**清理 `diagnosis_run_state.messages_json`（存的是 pydantic-ai 的完整消息历史，见 `app/models/run_state.py:1-8` 注释）、`diagnosis_runtime_event.payload`、`diagnosis_usage_ledger`、`diagnosis_submission`、`audit_logs.input/output`。对照 `app/services/diagnostics/chats.py:134-143` 的删对话路径：它显式删了 `DiagnosisJob`、`DiagnosisRunState`、`KnowledgeMemory`，把 `AuditLog.input/output` 置空（`:139-140`），并删 `DiagnosisRuntimeEvent`（`:141`）。两条「删除」路径的彻底程度不同，但对外都宣称成功。关键放大因素：`app/models/run_state.py:20` 声明了 `foreign_key="diagnosis_reports.id"`，但 `migrations/versions/e3f4a5b6c7d8_add_diagnosis_cancel_and_run_state.py:28-38` 建表时**没有任何 `ForeignKeyConstraint`**，后续迁移也没补（已 grep 全部 `create_foreign_key`），因此数据库里不存在这条 FK，删除 report 时既不会级联也不会报错，只会静默产生孤儿行。
- **风险**：运维（或合规）执行「清理历史」后，被删报告的完整提问、模型回答、工具调用与工具返回内容仍以 `messages_json` / `payload` 原文形式留在库中，且因为父行已删、又没有 FK，**无法通过外键枚举这些孤儿**，只能靠 `report_id NOT IN (SELECT id FROM diagnosis_reports)` 这种手工反连接发现。影响面是全部租户的全部历史诊断。用磁盘和 PII 角度说：报告表清了、体积最大的那张表没清。删对话路径做对了，说明团队知道要清什么——问题出在这条路径漏了。
- **业界做法**：SaaS 多租户的标准做法是把「删除」收敛成单一删除服务（storage/schema 级联），并在 schema 上声明 `ON DELETE CASCADE`（PG）或用 `partition by org` + `DROP PARTITION` 做批量清理；GDPR/等保语境下要求「删除请求可验证」——通常配一个 `deletion_receipts` 表记录实际影响行数，并定期跑 orphan 检测任务（如 `orphaned_rows` 指标）纳入告警。数据保留策略一般落在 `retention_policy` 配置 + 定时任务，而不是散落在两个 service 函数里。
- **可采纳性**：easy。改动集中在 `clear_diagnosis_reports` 一个函数：把 `chats.py:134-143` 的清理逻辑抽成共享的 `_purge_report_content(session, ids, org_id, system_id)`，两个调用点都调它；再新增一个迁移给 `diagnosis_run_state.report_id` 补上真实的 FK + `ON DELETE CASCADE`（或在模型层改用 `ondelete="CASCADE"` 并生成迁移）。注意补 FK 前必须先清理历史孤儿，否则迁移会失败——这是唯一需要小心的地方。
- **建议**：改 `backend/app/services/diagnostics/reports.py:213-234`（抽共享 purge 函数并补 `DiagnosisRunState` / `DiagnosisRuntimeEvent` / `AuditLog` 置空），新增迁移 `add_run_state_fk`（`op.create_foreign_key(..., ondelete="CASCADE")`，downgrade 里 `drop_constraint`）。预期收益：删除语义与宣传一致，孤儿行不再累积，`diagnosis_run_state` 的 FK 也不再只活在 metadata 里。

### [medium] 索引命名与覆盖范围在模型和迁移之间系统性漂移，autogenerate 的 diff 已不可信

- **证据**：实测 metadata（`SQLModel.metadata.tables`）与迁移产出的索引名成对不一致：`metric_samples` 迁移建 `ix_metric_samples_org` / `_system` / `_observed` / `_lookup`（`d2e3f4a5b6c7_add_metric_samples.py:26-30`），metadata 期望 `ix_metric_samples_org_id` / `_system_id` / `_observed_at`；`knowledge_memories` 迁移建 `ix_knowledge_memories_org` / `_system` / `_embedding`（`f8b9c0d1e2f3:47-55`），metadata 期望 `ix_knowledge_memories_org_id` / `_system_id` / `_diagnosis_report_id` / `_workflow_id`；`improvement_candidates` 迁移建 `_org` / `_system` / `_report` / `_status` / `_source`（`c1d2e3f4a5b6:52-56`），metadata 期望 `_org_id` / `_system_id` / `_report_id` / `_created_at` / `_reviewed_by` / `_memory_id`；`diagnosis_usage_ledger` 迁移建 `ix_usage_ledger_session` / `ix_usage_ledger_report`（`f4a5b6c7d8e9:56-61`），metadata 期望 6 个 `ix_diagnosis_usage_ledger_*`；`change_events` 迁移建 `ix_change_events_org` / `ix_change_events_system_time`（`b2c3d4e5f6a7:32-33`），metadata 期望 `ix_change_events_org_id` / `_system_id` / `_occurred_at`。另外迁移建了 `ix_diagnosis_reports_heartbeat`（`f4a5b6c7d8e9:35`）而模型未声明该索引（`diagnostics.py:46` 无 `index=True`）；反过来 `diagnostics.py:48` 的 `resumed_from_report_id` 带 `index=True`，会期望一个**多余的非唯一索引**叠在同列的部分唯一索引 `uq_diagnosis_resumed_from` 上。
- **风险**：只要有人跑一次 autogenerate，产出的是一个几十行的「加 20 个同名不同后缀的索引 + 删 20 个旧索引」的巨型 diff。真实后果有两层：(1) 这种 diff 没人会仔细审，第 1 条 finding 的 DROP 语句就藏在里面被一起放过——这是「高危项能长期存在」的直接原因；(2) 若真的执行，`CREATE INDEX`（非 CONCURRENTLY）会在大表上持 ACCESS EXCLUSIVE 锁，配合启动期迁移会阻塞写入。等于 Alembic 最重要的安全网已经失效。
- **业界做法**：统一用 SQLAlchemy 的 `naming_convention`（`MetaData(naming_convention={"ix": "ix_%(table_name)s_%(column_0_N_name)s"})`）让模型与迁移生成同一套名字，pgvector/云原生项目普遍如此；Alembic 官方文档也建议在 `env.py` 里设置 `target_metadata.naming_convention`，并在 CI 跑 `alembic check` 作为「模型=schema」的门禁。对已存在的库，多数团队选择一次性「改名迁移」把索引统一到 convention，之后 autogenerate 就是干净的空 diff。
- **可采纳性**：moderate。改 `naming_convention` 需要一次性改名迁移（28 个 revision 里涉及约 25 个索引），并且要在大表上重建索引；`ix_metric_samples_lookup` / `ix_usage_ledger_session` / `ix_change_events_system_time` 这类复合索引还得显式写进模型的 `__table_args__`。工作量真实但不涉及架构重构，收益是恢复 autogenerate 与 `alembic check` 能力。
- **建议**：先在 `backend/migrations/env.py` 给 `SQLModel.metadata` 设 `naming_convention`，然后生成一个「只改索引名」的迁移重命名为 convention 形态，并把 3 个复合索引补进 `app/models/` 对应 `__table_args__`；最后在 CI 加 `alembic check`。预期收益：模型与库不再漂移，`--autogenerate` 可安全使用。

### [medium] 删除「系统」在有历史数据时必然 500：全库没有任何 `ON DELETE` / 级联，前置校验只检查了 services

- **证据**：`app/services/systems/service.py:181-187` 的 `delete_system` 只在「系统下还有服务」时抛 `ValueError`（`:183-184`），然后调 `delete_system_for_org`；`app/repositories/systems.py:53-58` 直接 `session.delete(system); session.commit()`。但 `systems` 在 Postgres 里有 9 张 FK 子表——`collectors`（`238f4c603dd8_initial.py:72`）、`services`（`:86`）、`action_workflows`（`9e4a8f7e6f31:59`）、`system_messages`（`4b6a8c2d91f0:43`）、`system_tokens`（`a91c20b73f41:36`）、`audit_logs`（`d3f2c8a71e09:37`）、`diagnosis_reports`（`f1a2b3c4d5e6:44`）、`incidents`（`b8c9d0e1f2a3:37`）、`notification_deliveries`（`c4d5e6f7a8b9:42`）——且全仓**没有任何 `ondelete=`/`cascade=`**（已 grep），模型里也**没有任何 `relationship()`**（已 grep `app/models/`），所以 ORM 层不会代为级联。`app/api/systems.py:121-132` 的 handler 只捕获 `LookupError` / `ValueError`，`IntegrityError` 会直接冒成 500。
- **风险**：触发路径是**被前置校验逼出来的常规操作**：运维想删系统 → 先删掉全部 service（`services/systems/lifecycle.py:240` 是硬删）→ 再删系统 → `audit_logs.system_id` / `diagnosis_reports.system_id` / `collectors.system_id` 中任意一张有行就抛 FK 违例 → 500。而 `audit_logs` 在诊断、日志分析、数据分析、工作流、OpenAPI 调用等大量路径上都会带 `system_id` 写入（`app/services/audit.py:26,59,67`，调用点遍布 `services/openapi.py`、`services/workflows/service.py`、`services/log_analysis.py`、`services/data_analysis.py`），所以**任何跑过一次业务的系统都删不掉**，只能靠直接连库手工清。这是「管理端点在生产上不可用」，不涉及数据丢失。
- **业界做法**：SaaS 多租户的通行做法是**软删 + 异步硬删**：`systems.deleted_at` 置位并立刻从所有读路径过滤，真正的级联清理交给后台任务分批执行（避免长事务与锁等待）；schema 层用 `ON DELETE CASCADE` 表达从属关系，对审计类表（`audit_logs`）故意用 `ON DELETE RESTRICT` 并在应用里做「归档到冷存储再删」的编排。云原生项目的等价物是 K8s 的 ownerReference + finalizer 模式：删除请求先标记、由控制器完成级联。
- **可采纳性**：moderate。要区分「从属数据」（`services`/`collectors`/`system_tokens`/`action_workflows`/`notification_deliveries`/`incidents` 可以级联删）与「审计与历史」（`audit_logs`/`diagnosis_reports`/`system_messages` 应当保留并做 `org_id` 置空或归档），这个策略决定需要产品确认，不是纯技术改动；迁移侧给 9 张表补/改 FK 也需要在大表上加约束（`ALTER TABLE ... ADD CONSTRAINT` 会全表校验并持锁）。
- **建议**：短期先修 `backend/app/services/systems/service.py:181-187`，把校验扩展为对全部子表计数，明确返回 409 并列出阻塞对象和行数（比 500 可诊断得多）；中期新增迁移给从属表补 `ondelete="CASCADE"`、给 `audit_logs`/`diagnosis_reports` 保留 RESTRICT 并在 service 层实现「先归档再删」。预期收益：端点从「必然 500」变为可预期行为。

### [medium] `business_context` 一个 JSON 字段承载 9 种互不相关的语义，其中路由键 `chat_id` 被用在无表达式索引的 JSON 过滤里；且列对话时会「读一次写一次」

ADD VALUE` 演进），或退一步用 `status_lookup` 维表 + FK；应用侧用 Python `enum.StrEnum` 单一来源生成字面量，并由 Alembic 迁移从 enum 生成 CHECK 表达式，避免两处手写。事件驱动的 Agent 平台更进一步把状态迁移记成 append-only 的 `state_transitions` 事件表（当前状态由事件投影得到），这样「谁在什么时候把状态改成了什么」可审计——比一个可变 `status` 列更适合诊断/审批这种需要留痕的场景。

### [medium] 时间戳一半是 `timestamptz`、一半是 `timestamp`，应用把 aware UTC 写进 naive 列，且容器未固定 DB 时区

- **证据**：迁移里两种类型混用——`f1a2b3c4d5e6_add_diagnosis_reports.py:42` 建 `created_at sa.DateTime()`（即 `timestamp without time zone`），`c1d2e3f4a5b6:27,48` 建 `feedback_at` / `created_at` 用 `sa.DateTime(timezone=True)`（`timestamptz`），`b2c3d4e5f6a7:29-30`、`e3f4a5b6c7d8:36-37`、`f4a5b6c7d8e9:54`、`f7a8b9c0d1e2:39,50`、`f8b9c0d1e2f3:44-45` 又是 `timezone=True` 且 `server_default=now()`。而模型统一用 aware UTC（`app/models/common.py:5-6`），SQLAlchemy 侧声明的是裸 `datetime`（如 `diagnostics.py:58`、`monitoring.py:22`），于是**同一个库里的时间列，一半由 Python 写 aware 值、一半由 DB 的 `now()` 生成**。代码里到处出现「事后补 tzinfo」的补丁，正说明这个不一致是真实存在的：`services/diagnostics/jobs.py:22-23` 的 `aware()`、`services/diagnostics/usage.py:461-464` 的 `_aware()`、`services/monitoring/scheduled.py:48` 的 `last.replace(tzinfo=timezone.utc)`、`services/monitoring/trend.py:191-192` 的同款处理。运行时配置侧：`app/core/database.py:13` 的 `create_engine` 未设 `connect_args={"options": "-c timezone=UTC"}`，`deploy/docker-compose.yml:2-16` 的 `platform-db` 也只设了账号密码、**没有设 `TZ`/`PGTZ`**（对比 `app/workers/celery.py:24` 明确写了 `celery.conf.timezone = "Asia/Shanghai"`）。
- **风险**：Postgres 把 aware 值写入 `timestamp without time zone` 列时，会先按会话 `TimeZone` 换算再存裸值。当前 PG 官方镜像通常落在 UTC 上，所以今天是「恰好正确」；一旦 DB 容器/托管实例的 `TimeZone` 不是 UTC（RDS 默认常随参数组变化、自建库常见 `Asia/Shanghai`），所有 `timestamp` 列会整体偏移 8 小时，并且**读回来是 naive**，与 `datetime.now(timezone.utc)` 相减直接抛 `TypeError: can't compare offset-naive and offset-aware datetimes`。最可能的爆点是诊断会话窗口与预算窗口：`usage.py:285`（另见 `:369,416`）的 `_window_start(now)` 与从库里读回的 `window_started_at` 混算，`usage.py:361,447` 已经要靠 `_aware()` 兜；任何漏兜的新代码都会在非 UTC 库上炸。影响面是全部租户的时间语义与记账窗口。反过来，`server_default=now()` 的表（`knowledge_memories`、`metric_samples`、`improvement_candidates`、`change_events`）严格说是「DB 本地时间语义」，与同库其它表的 UTC 语义不同源，跨表 JOIN 排序会错。
- **业界做法**：所有时间列统一 `timestamptz` + 全库时区固定 UTC 是云原生的默认规范（AWS RDS 参数组、GCP Cloud SQL 都建议 `timezone=UTC`）；连接串层面强制会话语义（psycopg2 的 `options=-c timezone=UTC` 或 `SET TIME ZONE 'UTC'`），应用层只写 aware UTC 或统一只写 DB 侧 `now()` 而不混用。演进路径通常是「一次迁移把所有 `timestamp` 列 `ALTER ... TYPE timestamptz USING col AT TIME ZONE 'UTC'` + 在 connection 事件里固定时区」。也有团队用 `pydantic` 的 `AwareDatetime` 注解在边界拦住 naive 值。
- **可采纳性**：moderate。类型统一迁移要在多张表上 `ALTER COLUMN TYPE`（PG 需要重写表，大表会持锁；`metric_samples`/`diagnosis_reports` 上要按维护窗口做），并需要一次性决定「既有裸值按 UTC 还是按 DB 本地解释」——选错会整体偏移。连接层固定时区是一行改动、收益立竿见影。
- **建议**：先做低成本的一半——`backend/app/core/database.py:13` 的 `create_engine` 给 PG 分支加 `connect_args={"options": "-c timezone=UTC"}`，并在 `deploy/docker-compose.yml:2-16` 的 `platform-db` 显式设 `TZ=UTC`（这一步就把风险从「取决于运行环境」变成「确定」）；再新增迁移把 `timestamp` 列统一改成 `timestamptz`，且明确 `USING col AT TIME ZONE 'UTC'`。预期收益：跨表时间可比、naive/aware 混算的 `TypeError` 绝迹。

### [medium] 唯一性只在应用层检查，数据库没有约束；SQLite 兜底路径的 FK 完全形同虚设

- **证据**：`systems.key` 在模型里只有 `index=True`（`app/models/systems.py:15`），迁移同（`238f4c603dd8_initial.py:46`），唯一性靠 `app/services/systems/service.py:110-111` 的 `if get_system_by_key(session, org_id, body.key): raise` —— 典型的 check-then-insert，两个并发创建请求可同时通过检查（无唯一索引 → 无冲突异常可捕获），之后 `get_system_by_key`（`repositories/systems.py:16-22`）用 `.first()` 返回**任意一行**。凭据查询列同样只有普通索引：`SystemToken.token_hash`（`tokens.py:18` + `a91c20b73f41:43` 的 `unique=False`）与 `Collector.token_hash`（`collectors.py:16` + `238f4c603dd8:78` 的 `unique=False`），但它们是**唯一**的查找键——`repositories/tokens.py:24-27` 的 `get_token_by_hash` 与 `core/deps.py:43-45` 的采集器鉴权都是 `WHERE token_hash = ?` 后 `.first()`，没有任何 `org_id`/`system_id` 参与。对比之下 `users.email` 是有 `unique=True` 的（`models/auth.py:20`），说明团队知道该加，只是没加全。另外 SQLite 侧：`database.py:12,13` 的 `create_engine` 只设了 `check_same_thread`，全仓**没有 `PRAGMA foreign_keys=ON`**（已 grep），SQLite 默认不强制外键，所以 `create_all` 建出来的那些 FK 在 dev 环境里全是装饰——`diagnosis_run_state.report_id` 的「模型有 FK、Postgres 库里没有」（见上一条）在 SQLite 上则变成「DDL 有 FK、运行时也不强制」。
- **风险**：(a) `systems.key` 是外部 OpenAPI 的身份解析键（`api/openapi.py:71` 用 `get_system_by_key(session, token.org_id, system_code)`），重复 key 会让同一 org 内两个系统互相「抢」同一个 `system_code`，`token.system_id != system.id` 的分支（`openapi.py:72-73`）随机返回 403——表现为间歇性鉴权失败，而不是明确报错。触发条件是并发创建或绕过 service 层的写入（脚本、迁移、人工 SQL），概率不高但一旦发生难以定位。(b) 凭据哈希列无唯一约束意味着 `SELECT ... LIMIT 1` 不是全函数；虽然 key 由 `secrets.token_urlsafe(32)`（`core/security.py:126-127`）随机生成、碰撞不现实，但「凭据解析靠一个非唯一列的第一行」在安全审计里是不可接受的模式。(c) SQLite 不强制 FK 会让 dev 环境掩盖级联/引用错误，与生产行为不一致——正是这种不一致让「删系统 500」这类问题只在生产暴露。
- **业界做法**：任何被当作查找键或凭据的列一律加 `UNIQUE`（凭据哈希用唯一索引 + 常量时间比较）；业务唯一键用**部分唯一索引**表达 `UNIQUE (org_id, key)`（这里 `key` 的语义是 per-org 唯一，天然适合 `UniqueConstraint("org_id","key")`，也顺带让 `systems.key` 的复合索引服务 `get_system_by_key`）。SQLite 场景在 SQLAlchemy 里用 `event.listens_for(Engine, "connect")` 执行 `PRAGMA foreign_keys=ON`，或干脆让 dev 也用 Postgres（testcontainers）以消除方言差异——后者是当前多数云原生团队的选择。
- **可采纳性**：easy。加约束需要先清洗重复数据（迁移里 `DELETE`/合并重复 key，并在应用层把「重复 key」改为返回 409）。`PRAGMA foreign_keys=ON` 是十来行改动，但启用后可能立刻暴露出 dev 数据里既有的悬空引用（需要一次性清理），这一点要有心理准备。
- **建议**：新增迁移给 `systems` 加 `UniqueConstraint("org_id","key")`、给 `system_tokens.token_hash` 与 `collectors.token_hash` 加 `unique=True`（先跑一次重复数据检测并人工确认）；在 `backend/app/core/database.py` 加 SQLite 的 `PRAGMA foreign_keys=ON` 事件监听。预期收益：并发唯一性由 DB 保证，凭据查找成为全函数，dev/prod FK 语义一致。

### [medium] 迁移在进程启动时执行、无锁、一次部署执行两次，且全部 revision 在同一事务里用非 CONCURRENTLY 建索引

- **证据**：`app/core/database.py:90-100` 的 `_run_alembic_upgrade()` 被 `init_db()`（`:75-83`）调用，`init_db()` 挂在 FastAPI lifespan（`app/main.py:90`）；同时 `deploy/docker-compose.yml:41` 的启动命令是 `alembic upgrade head && uvicorn app.main:app ...`——**同一次启动会把 `upgrade head` 跑两遍**（第二次是 no-op，但两次都要连库、都要读 `alembic_version`）。没有任何互斥机制：`_run_alembic_upgrade` 里只设了 `configure_logger`（`database.py:99`），没有 PG advisory lock；`alembic.ini` 全文件**没有 `transaction_per_migration`** 设置，因此 28 个 revision 在 PG 上共用一个事务。启动路径还顺带做了写操作：`database.py:84-87` 在每次启动时调用 `backfill_incidents(session)`，而 `services/incidents/service.py:63-83` 是 `find_open_incident` 后 `session.add(Incident(...))` 的 find-or-create，`incidents` 表上没有任何唯一约束（`b8c9d0e1f2a3:22-39`）。
- **风险**：(a) 多副本/滚动发布时两个 API 进程会并发执行 DDL——`CREATE INDEX`/`CREATE TABLE` 竞态会抛 `relation already exists` 或 `duplicate key value violates unique constraint "alembic_version_pkc"`，结果是**进程启动失败**，而不是某个人工操作的失败；`docker compose up --scale platform-api=2` 或任何 K8s 滚动更新就是触发条件（当前 compose 是单副本 + worker 靠 `service_healthy` 串行化，所以默认部署暂时安全，这个风险被部署形态掩盖了）。(b) 28 个 revision 单事务 + 非并发建索引，在有数据的库上升级会在 `diagnosis_reports`、`metric_samples`、`knowledge_chunks` 上持 ACCESS EXCLUSIVE 锁，升级期间该库**写全阻塞**，而这段时间正是启动窗口。(c) 启动期 `backfill_incidents` 在多副本下并发执行，两个进程可能都读到同一批 `incident_id IS NULL` 的消息，各自 `add` 一条 incident，产生重复工单（无唯一约束兜底）。
- **业界做法**：迁移与进程启动解耦是云原生共识——迁移作为独立的一次性 Job / init container（`docker run ... alembic upgrade head`）在滚动发布前完成，应用容器只等待 schema 版本满足后启动；必须并发安全时用 PG advisory lock（`SELECT pg_advisory_lock(<const>)`，Alembic 生态有 `alembic-pg-advisory-lock` / 自写 `env.py` 钩子）或 Alembic 官方 `--sql` + 人工 gate。大表索引用 `CREATE INDEX CONCURRENTLY`（Alembic 里 `op.create_index(..., postgresql_concurrently=True)` 需配 `transaction_per_migration=True` 或 `autocommit_block()`）。启动期数据回填改造成带唯一约束的幂等任务（`INSERT ... ON CONFLICT DO NOTHING`）。
