# Agent 核心（backend/app/agent/** + agent-runtime/） 体检

## 现状设计

工具能力由 harness/catalog.py 的 tool_catalog() 从 diagnostics/tools.py 的函数签名反射生成（strict + extra='forbid' 的入参模型、risk/timeout/freshness/retryable/replayable 元数据），所有执行路径统一汇入 harness/gateway.py 的 ToolGateway.invoke：先做 expected_scope 相等校验（RunScope 含 org_id/system_id/run_id）、工具许可白名单、入参模型校验、ops_policy 的 Redis/Kafka 只读白名单授权，再经 AdmissionBudget 扣减请求/工具预算，然后分派到 asyncio 或 ExecutionTracker 的线程池执行，最后强制写审计并给所有输出套外部数据边界。执行生命周期用 ExecutionTracker 区分"已停止等待"与"已确认停止"，未确认则抛 ExecutionUnsettled 并禁用 resume；预算/审计/取消/上下文通过 dataclasses.replace 的 child_context 原样继承给子代理，子代理工具集只做交集收窄。上下文侧按"稳定前缀（目录、规则）+ 易变尾部（技能、时钟、知识库、对话、图片）"拼装系统提示，外部数据一律 JSON 编码后包进显式边界标记并转义正文中的标记。多引擎通过 runtime/contracts.py 的 AgentRuntime 协议抽象，engine 显式选择且禁止静默跨引擎降级，历史按引擎分别版本化；Pi 试点走 HTTP + Redis pub/sub 反向工具回调，受 loopback 地址、共享密钥、协议版本与本机 SQLite 单属主日志约束。

## 做得好的地方

- 权柄单一来源且四条执行路径共用同一道闸门：catalog.py:39-54 反射生成工具目录，gateway.py:66-169 集中做 scope/许可/入参/策略/预算/取消/审计，Pydantic 工具（tool_adapter.py:21-35 的 bind_tool）、Pi 桥接（bridge.py:82）、MCP Server（mcp_server.py:105）、MCP Client 全部复用同一 ToolGateway，提示词与文档文本无法凭文本扩张权限。
- 审计与结算 fail-closed 且语义严谨：审计写入失败时在'执行前'直接抛 ToolAuditError 拒绝执行（gateway.py:105-112），执行后审计失败也不自动重跑（gateway.py:160-169）；execution.py:20-21/63-83 用 ExecutionTracker._confirmed() 明确区分'停止等待'与'停止执行'，runner.py:453-463 未确认即抛 ExecutionUnsettled 并令 resume_safe=False；pi_runtime.py:174-178 与 runtime.js:134-146 都把'查询超时'当作 stop_unconfirmed 而非成功。
- 证据校验的自我克制有明确代码边界：evidence.py:1-5 与 claims.py:1-5 明示'成功调用不证明结论正确'，claims.py:93 恒返回 complete_answer_verified=False，只做显式 dataset_total 与受限 health 声明的一致性检查；freshness 与 resume 共用同一 TTL 策略（freshness.py:6-7），缓存命中明确不算新观测（claims.py:69、health_claims.py:25）；apply_evidence_guard 把'没有取证工具'/'取证工具失败'/'声明与证据冲突'分成三种 reason，且校验器异常绝不重跑模型（evidence.py:64-82）。
- 提示注入防护是边界级而非逐工具级：gateway.py:144-145 在网关出口对每一个工具结果统一套 external_text，context_data.py:22-24 会转义正文里伪造的边界标记，context_data.py:61-73 用字段白名单投影 descriptor 并剥掉 URL 的 userinfo/query，连降级纯文本路径也走 model_descriptor（runner.py:544-548），不泄密到模型侧。
- 委派只收窄不放宽并有完整审计闭环：delegation.py:6-15 用 child_context 把子代理工具集与父集合求交、给子调用加 call_id 命名空间、并原样继承 cancel_token/execution_tracker/tool_audit_sink/双预算；tool_adapter.py:12-18 让子代理复用父 usage 与 usage_limits 而非另开预算；runner.py:324-336 与 476-494 把子代理取证步骤合并回主审计链，取消分支也一并带回。
- 跨引擎隔离与可验证续跑：factory.py:5-16 对未知引擎和未启用的 Pi 一律抛 RuntimeCompatibilityError 而非降级；pi_history.py:12-30 与 pydantic_history.py:13-33 逐字段校验身份、版本、scope、消息结构与用量基线，缺基线时拒绝按零用量恢复；Pi 侧 pi_runtime.py:60-76 强制 loopback + 共享密钥 + /healthz 协议版本握手，runtime.js:21-41 在服务端二次校验 run_id/scope/limits 与每个工具的 input_schema，store.js:14-26 用 pid 属主锁与 WAL 标记进程被杀的在途运行为 process_lost。

### [high] search_knowledge_base 因 id 形状不一致永久查不到任何知识库文档（静默失效）

- **证据**：agent/diagnostics/tools.py:598 `system_id = ctx.deps.descriptor.get("id", "default")`，而 descriptor["id"] 由 services/descriptors/builder.py:52 生成为 `f"org{system.org_id}-{system.key}"`（非数字）。knowledge/store.py:190-196 的 _as_int_system_id 对非数字返回 None，于是 store.py:203 `if not docs_dir.exists() or _as_int_system_id(system_id) is None: return False` 使 _sync_index 恒为 False、_vector_hits 恒为 []；降级路径 _keyword_hits 读的是不存在的 DOCS_ROOT/"org1-xxx" 目录（磁盘上实际是 knowledge/docs/1、knowledge/docs/3），返回 []；search_with_memories 又因 store.py:347-349 `sid = _as_int_system_id(system_id); if sid is None: return hits` 直接跳过结构化记忆。最终 tools.py:600-601 恒返回「知识库中暂无相关记录」。对照证据：service.py:954、api/knowledge_base.py:114、services/diagnostics/evidence.py:186 全部传 `str(system.id)`；runner.py:619 已把回写侧改成 `str(system_id)`，且 runner.py:317-318 的注释正好记录了同类历史 bug（『旧版用 descriptor id 建目录，检索却查 docs/<数字id>，经验回写从未被命中过』）——读侧漏改。
- **风险**：100% 复现、无任何日志或异常：只要问题命中 prompt.py:32/45 强制的『含告警代号先 search_knowledge_base』路径，或本轮被判定为 availability_only 而抑制了 knowledge_context 注入（service.py:953-954 明确注释『Knowledge remains available through tools』），agent 就拿不到任何知识库内容，并按 prompt.py:42 的规则在「关键证据」里写下『知识库无匹配记录』——向用户输出一个自信的错误前提。同时 UI 的证据链面板（evidence.py:186 用数字 id）会照常列出知识库引用，形成『界面有引用、agent 说无匹配』的自相矛盾。影响面：所有系统的 agent 侧显式知识库检索与结构化记忆合并，等于一条核心能力被静默关闭。
- **业界做法**：业界多租户知识库检索普遍坚持『租户键在整条链路上只有一个规范形式』：Elasticsearch/OpenSearch 用 routing + filter 而非目录名做隔离；pgvector/LangChain 的 retriever 明确把 tenant_id 作为必填参数并在检索前做一次 assert；SaaS 常见做法是给每个入口写同一份 tenant-resolver（如 Django 的 TenantMiddleware、multi-tenant 下的 scoped manager），并在 CI 里加一条『同一 resource 的所有读写路径使用同一 key 函数』的不变量测试。
- **可采纳性**：easy
- **建议**：把 tools.py:594-610 的 search_knowledge_base 改为使用与其余入口一致的规范键：从 scope 取数字 id（`getattr(ctx.deps.scope, "system_id", 0)`），并在 AgentDeps 上新增一个显式的 `knowledge_system_id` 字段，由 service.py:951 构造 descriptor 时用 `str(system.id)` 注入，agent 侧不再猜。同时把 store.py 的 _as_int_system_id 失败路径从静默返回 [] 改为 logger.warning（含原始 id），并加一条单测：同一 system 经 send_message/resume/子代理三种路径调用 search_knowledge_base 必须返回同一批命中。预期收益：直接恢复被静默关闭的知识库与结构化记忆检索，消除 UI 与 agent 结论的矛盾。

### [high] MCP 第三方 server 子进程继承平台全量环境变量（凭据外泄面）

- **证据**：agent/diagnostics/mcp.py:128-135 `StdioServerParameters(command=server.command, args=list(server.args), env={**os.environ, **server.env})`，且 mcp.py:157-177 的 _call_tool 每次调用都会 stdio_client 启动一次该第三方进程。被继承的进程环境包含 core/config.py:48 database_url、51 jwt_secret（默认 'dev-secret-change-me-in-prod'）、59 pi_service_secret、82 deepseek_api_key、110 embedding_api_key、121 rerank_api_key、126 langfuse_secret_key、131 feishu_app_secret、139 celery_broker_url。MCP SDK 自身的 StdioServerParameters 文档写的是『Extra environment variables, merged over get_default_environment()』，即 SDK 本已提供安全默认环境集 get_default_environment()，此处用 os.environ 把它整个绕过。平台对 MCP 的信任模型本身是『外部不可信』（mcp.py:1-8 明示输出当作外部数据、mcp.py:123-125 要求 org_ids/system_ids 显式授权），环境继承与该模型自相矛盾。
- **风险**：任何被配置进来的 MCP server（第三方 SDK、外部厂商提供的 k8s/云平台/工单连接器）都能在启动瞬间读到平台 JWT 签名密钥、数据库连接串、LLM/embedding/rerank API Key、飞书 app secret 与 Celery broker 地址。触发条件仅需运维按文档加一条 MCP_SERVERS 配置（无需任何代码改动），而 MCP server 是被当作半可信外部组件引入的。拿到 jwt_secret 可直接伪造任意 org/user 的令牌 → 跨租户越权；拿到 database_url 可直接读写全租户数据。影响面为全平台，且默认配置（mcp_servers 为空）下不暴露，属于配置引入型高危。
- **业界做法**：容器与子进程隔离的标准做法是显式 allowlist 传递环境：Docker/K8s 默认不继承宿主 env，必须逐项声明（compose 的 `environment:`、k8s 的 `env:`/`envFrom` 指定 ConfigMap/Secret）；AWS/GCP 用 instance role / Workload Identity 避免把长期凭据放进环境；Vault Agent / External Secrets 做按服务注凭据；应用侧常见 `subprocess` 传 `env=` 白名单（12-factor 强调 config 进环境但按进程最小化），MCP 生态自身的 `get_default_environment()` 就是这一原则的实现。
- **可采纳性**：easy
- **建议**：改 mcp.py:128-135，删掉 `**os.environ` 展开：`env=dict(server.env)`（None/空则让 SDK 走 get_default_environment()），并在 load_servers（mcp.py:47-95）里对 server.env 的 key 做一份禁止名单校验（拒绝 DATABASE_URL/JWT_SECRET/*_API_KEY/*_SECRET 等前缀），启动时把最终传给子进程的 env key 列表打一条 INFO 日志供审计。若确需给 MCP server 凭据，走 MCPServer.env 显式声明并在配置文档里标注。预期收益：把『配置一个 MCP server』从等价于『交出平台全部密钥』降为『只交出该 server 明确声明的凭据』。

### [medium] 全局单例 8 线程执行池跨 run/租户共享，排队延迟被上报成工具超时

- **证据**：harness/execution.py:23 `_EXECUTOR = ThreadPoolExecutor(max_workers=8, thread_name_prefix='diagnosis-tool')` 是模块级进程级单例，被所有 run、所有租户、所有父/子代理共用；gateway.py:100-104 对同步工具执行 `tracker.submit(call_id, ...)`，队列无界；gateway.py:116-122 用 `asyncio.wait_for(wait_result(), spec.timeout_seconds)` 计时，而 catalog.py:51 给同步读工具的超时是 60s、sandbox/delegation 是 300s。超时后 gateway.py:134-135 统一产出 `'工具超时：停止等待；底层同步操作可能仍在收尾，不自动重试'`（status='timeout'），与『已在执行但未完成』无法区分。放大因素：specialists.py:62-65 一次 consult_specialists 并发拉起 4 个子代理（specialists.py:44 共享同一 tracker 与 tool_cache），pydantic-ai 单轮可并行发多个工具调用，单次诊断的工具预算上限为 24（config.py:98），因此一个复杂排查很容易同时占用 ≥8 个 worker。gateway.py:102 在 tracker 为 None 时退回 asyncio.to_thread，用的是解释器默认无界线程池，问题同源。
- **风险**：当同进程内有多个并发诊断（或单个诊断扇出 4 个专家）同时发起慢工具调用时，8 个 worker 被占满，后续 submit 进入无界队列但不开始执行；等待计满 60s 后该工具被判定 timeout，agent 收到『工具超时』并据此改变排查策略或直接下结论——而事实上该工具从未被执行（或稍后才执行并产生晚到结果被丢弃，gateway.py:127-128）。表现为：高负载下诊断质量骤降、超时率与并发数强相关、单租户的慢工具可以拖垮其他租户的诊断（缺少 bulkhead 隔离）。
- **业界做法**：云原生与 SaaS 的标准做法是舱壁隔离：每个 run/租户/工具类别独立有界线程池或信号量（Resilience4j 的 Bulkhead、Hystrix 线程池隔离、Envoy 的并发限制与 circuit breaking）；对『排队时间』与『执行时间』分别设限并分别上报（如 gRPC deadline + queue timeout、Java 的 RejectedExecutionHandler + CallerRunsPolicy）；对同步阻塞型外围调用改为异步 I/O 或独立的工作进程池，避免共享一个有界线程池。
- **可采纳性**：moderate
- **建议**：三处改动：(1) 把 execution.py:23 的全局池改为按 run（或按 ScopeValue.run_id 哈希分桶，例如 8 个 size=4 的有界池 + 每池有界队列）分配，队列满时立即返回 429/'工具排队已满' 而不是静默排队，让网关能把『排队失败』与『执行超时』分成不同 error_code；(2) gateway.py:116-122 增加独立的排队计时，超时时区分 'deadline_exceeded'（已开始执行）与 'queue_timeout'（未开始执行）；(3) 把 specialists.py:62-65 的并发专家数纳入同一舱壁配额并显式限制（例如同时最多 2 个专家），或让 consult_specialists 在池饱和时降级为串行。预期收益：消除跨租户互相拖垮与『未执行却报超时』的误判，为容量规划提供可测指标。

### [medium] 重排在截断后的 6 条候选上执行，候选池 16 被浪费，TOP_K 为死配置

- **证据**：knowledge/store.py:38 `RERANK_POOL = 16` 并提供 16 条候选（store.py:411 `"k": RERANK_POOL`，关键词路径 store.py:455 同样返回 16 条），store.py:321 的调用顺序是 `hits = _dedupe_hits(hits); hits = rerank_documents(query, hits); return _apply_budget(hits, max_chars)`。但 knowledge/rerank.py:19 定义 `MAX_CANDIDATES = 6`，rerank.py:128 在真正打分前就 `docs = docs[:MAX_CANDIDATES]`。因此向量序第 7-16 名的片段永远不会进入重排器——重排只能对已经按『向量距离』排好的前 6 名重新排序，无法把第 7 名提到第 1 名，RERANK_POOL=16 的设计意图（为强重排提供更大召回池）未生效。另 store.py:35 的 `TOP_K = 6` 在全仓库无任何引用（grep 仅命中定义行），说明『先重排后取 top-k』的意图只实现了一半，实际生效的是 store.py:325-335 的字符预算裁剪。
- **风险**：当真实相关文档的向量相似度排在第 7-16 名（这正是 RERANK_POOL 存在的理由，也是 store.py:98-110 注释里描述过的『短片段向量相似度偏高，把真正正文块挤出 top-k』场景）时，强重排器无力纠正，检索表现为『文档里有却答不出』；启用 rerank API/LLM 的成本（rerank.py:45-65 或 rerank.py:103-120 的一次外部调用）只换来对 6 条候选的内部换序，投入产出严重不符。属于会持续消耗 token/费用并降低诊断质量的静默技术债。
- **业界做法**：标准两阶段检索的实现是『大池召回 → 全池重排 → 取 top-k』：Cohere Rerank 官方建议对 top-50~100 候选重排后只保留 top-3~5；LlamaIndex 的 SentenceWindowNodePostprocessor / CohereRerank 的 `top_n` 明确作用在召回池上；Elasticsearch 的 RRF/rerank 也是在 retrieve 阶段（大 pool）之后再 rank 阶段做截断。关键点是 top-k 的截断必须发生在重排之后。
- **可采纳性**：easy
- **建议**：改 knowledge/rerank.py:123-141：把 `docs = docs[:MAX_CANDIDATES]` 的截断移除（或改为由调用方传入的 pool 大小，默认等于 store.RERANK_POOL=16），并把最终 top-k 交给调用方——在 store.py:313-322 于 rerank 之后用 `TOP_K` 做真正的截断（`return _apply_budget(hits[:TOP_K], max_chars)`），让 TOP_K 从死配置变成生效参数。同时给 rerank 加一条断言/日志：进入重排的候选数 == 召回池大小，防止再次被静默截断。预期收益：让已付费的重排器真正发挥作用，提升『文档存在即可被引用』的命中率。

### [medium] 工具结果状态归一化用子串匹配，成功输出会被误判为 denied

- **证据**：harness/evidence.py:92-96 的 outcome_for_text 中：`if any(marker in text for marker in ('工具访问被拒绝：', '提示注入防护：')): return 'denied', 'connector_denied'`——用的是**任意位置子串**匹配，而紧接其后的同函数其它判定（evidence.py:99-110）全部使用 `text.startswith(...)`。该函数是唯一的状态归一化入口，被 gateway.py:131-132 用于写审计记录、runner.py:594 用于生成报告里的 tool_calls.status。下游强依赖 status=='success'：evidence.py:39-47 的 evidence_available 要求 `call.get('status')=='success'`，claims.py:38/44 直接跳过非 success 的调用，tool_events.py:70-73 也会用 record 的 status 覆盖真实结果。触发条件很现实：平台会自监控 local 系统（prompt.py:15 的『平台托管』分支），读取自身日志时正文里必然出现网关产生的『工具访问被拒绝：』「提示注入防护：」字样；任何知识库文档、runbook、业务数据集字段值里引用这两句话也会命中。
- **风险**：一次成功的 read_logs/search_logs/search_knowledge_base 只要正文包含这两个短语之一，就会被记为 denied：审计链与报告里出现错误的工具状态（可追溯性受损）；该次调用不再计入 evidence_available，导致 apply_evidence_guard 在 evidence.py:75-77 给**本来有真实证据**的回答打上 flagged + reason='evidence_unavailable'，前端 EvidenceValidation.vue:11 随即展示『本轮诊断中未获得成功的取证工具结果』的告警。结果是正确回答被标注为未取证，持续侵蚀用户对校验机制（以及平台结论）的信任。自监控场景下几乎必然触发。

- **可采纳性**：easy
